## 0. 结论先行

0.2.16 的引擎已经能保证**结构正确**：阶段机、13 道门、八本台账、原子归档、崩溃恢复都有机械保证，1,206 项测试、94% 覆盖率。但它只保证「写对流程」，不保证「写得像这本书」——规则包里没有风格维度，设计资产提供的 8 份风格包在引擎里**零支持**（`src/` 与文档里 `grep -i "style.?pack"` 命中 0）。

0.2.17 做两件事：一件加法，一件减法。

| 方向               | 内容                                                                                                                                                                                                                          | 工作包         |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| **加法：文风层**   | 风格包 schema + 编译器 + 8 份内置包；10 条 `STYLE_*` 规则；7 条 `AI_TONE_*` 规则；创建期一次绑定、之后不可变；开书**与迁移**都由插件自己弹确认（`confirm:false` 可跳过）；P2–P6 任务书注入；面板与报告文风面                  | WP6–WP10、WP13 |
| **减法：证据收口** | 20 条 P1：字数口径、证据连续性、PG-09 数学、语义匹配器、词表误杀、锁基线、handoff、reopen、delta 丢弃、brief 预算、briefs 死锁、amend_issues、restore 护栏、锁回收、事务终态、面板 304/计数/刷新、批量任务书渲染、status 警告 | WP1–WP5        |

**一句话**：把「文风」从提示词里的形容词，变成可配置、可机检、可复盘的一等数据；同时把 20 处「门看起来在、其实没在」的洞补上。

排期约 **55.5 人日**（AI 辅助约 22–25 个工作日）。这不是补丁日，是「文风层 + 可信度」的完整 release。

### 0.1 三条必须先说清的事实

1. **设计资产不是「再抄一份 YAML」，是新规则族。** 684 行规则包里的 `lexicon.ai_tone` 有 7 类 39 条，带 `scope`（旁白/对白）、`window`、`escalation`、`replacement`、`false_positives`；现有编译器会把整个文件拒掉——`src/rules/compiler.ts:126-144` 的 root 白名单没有 `ai_tone`，`lexicon` 白名单 `:203-211` 也没有。缺的不是配置，是求值语义。

2. **8 份风格包与引擎有三处硬冲突，必须在编译期裁决。** ① `genres: [mystery, suspense, urban]` 是英文标签，引擎的 `GENRES` 是 12 个中文枚举（`src/types.ts:17-31`）；② `banned_patterns` 里的 `不是……而是……` 是模板不是子串，按 `includes` 匹配永远不中；③ `exemplars` 带人名，会随 npm 包发布，而随包产物要过 `tests/privacy.spec.ts:19-26` 的扫描（WP11 会把 `stylepacks/` 加进 `productRoots`）。三处都不能留给运行时「大概能跑」。

3. **20 条 P1 里有 4 条直接改变门的真假。** 全角缩进计词（`src/domain/wordcount.ts:7,41`）、证据可跨任意段拼接（`src/domain/text.ts:207-221`）、PG-09 在 1–2 段章节数学上不可满足（`src/engine/gates.ts:790-804`）、普通词 `话说/读者` 被当 blocker（`rulepacks/default.yaml:106,138`）。这四条不修，文风规则再准也不可信。

## 3. 目标与非目标

### 3.1 目标（可验收）

1. 风格是**书的属性**：在 `novel_init` 时由**用户确认**——插件自己弹窗，不靠 AI 自觉去问——之后**不可更改**；确认后，**规则、任务书、评审提示、面板**四处读到的是同一份风格定义。
2. 十条风格规则与七条 AI 腔规则都能在合成文本上稳定命中/不命中，且**默认不新增门控**：只有 `banned_patterns` 超过阈值才升级 blocker。
3. 20 条 P1 每条都有一条「旧实现必红、新实现必绿」的回归。
4. 8 份风格包通过编译与隐私扫描，`pnpm validate:stylepacks` 与 `pnpm check:pack` 全绿。

## 4. 口径与所有权裁决

这一节是整份方案的核心。**同一个语义只允许一个 owner**，否则 0.2.18 会来还债。

### 4.1 规则包与风格包的分工

| 维度   | 规则包（`rulepacks/default.yaml`）                  | 风格包（`stylepacks/*.yaml`）                                         |
| ------ | --------------------------------------------------- | --------------------------------------------------------------------- |
| 词     | 全局词表：零容忍、软限、元叙述、AI 腔条目           | 不拥有词表；只拥有 `banned_patterns` 这个**项目级补充**               |
| 阈值   | 全局阈值：段长 90、句号密度、破折号预算、查重相似度 | 风格阈值：句长分布、CV、段句数、对白区间、抽象情绪/比喻密度、爽点间隔 |
| 严重度 | 决定 blocker/advisory                               | 只决定「是否升级」：`banned_patterns` 超限才升级                      |
| 作用域 | 全书                                                | 单项目（`novel.yaml.style`）                                          |

**一句话**：规则包管「什么词不能说」，风格包管「这本书该长什么样」。

### 4.4 风格的绑定时机与不可变性

风格是**书的属性**，不是章节的证据。三态规则：

| 状态                  | 磁盘表示     | 能否设置                                                    | 规则                                         |
| --------------------- | ------------ | ----------------------------------------------------------- | -------------------------------------------- |
| 旧项目（早于 0.2.17） | `style` 缺失 | 仅当**零归档章**时，可设置一次，**且必须过确认门控**（C12） | 设置后立即转「已定」；已有归档章则永久无风格 |
| 已定                  | 8 个 id 之一 | 否                                                          | 任何 `novel_amend` 都被拒                    |
| 显式不启用            | `null`       | 否                                                          | 与「已定」同等不可变，只是规则休眠           |

**为什么必须不可变**：一旦允许中途切换，`novel_report` 的九项风格指标会把两套阈值的章节混在一起算均值，这个数字从此没有意义；已签的 P2/P3 任务书也会带着旧风格继续跑。把「切换」从能力里删掉，比给它写一套版本兼容规则便宜得多——上一版方案里的 `ChapterRecord.style_id`、`briefDependencies` 里挂 `style`、已归档章按谁判，这三个问题**全部消失**。

**为什么区分 `undefined` 与 `null`**：`undefined` 是「这个项目早于风格功能存在」，所以给一次迁移窗口；`null` 是「用户看过 8 份包后明确选择不用」，是主动决定，不给第二次机会。两者行为一致（规则休眠），语义不同。

**代价要认**：选错了只能新建项目。所以 `/novel style show <id>` 必须给出完整参数与规则清单，让「选错」尽量发生在选之前；WP13 在落盘前再弹一次确认，让「选错」也发生在**写之前**。若将来要开逃生口，应该是显式的 `novel_doctor` 子命令并记 journal，而不是悄悄放开 amend。

**为什么保留迁移窗口**：0.2.17 之前建的项目根本不知道有风格功能。若因为「建了项目但还没写」就永久锁死，等于把我们的发布时序转嫁给用户。零归档章保证不会有已归档章节混进两套阈值，所以窗口是安全的；但窗口必须与正门同一道确认（C12），否则它就是后门。

**迁移窗口的判定与确认是两件事**：`amendProblems`（`service.ts:12956`）判「能不能设」，WP13 判「用户同不同意」。前者是语义闸，后者在工具层、先于写盘发生。两者顺序是「先问 → 再走 amend → amendProblems 放行」，不是「amend 失败后再补问」。

### WP13 · 创建期与迁移确认门控（3.5 人日）— 执行位置：WP8 之后

**目标**：`novel_init` 与**迁移窗口的 `novel_amend`** 在**落盘之前**把不可变字段摆到用户面前确认一次；`confirm: false` 跳过。AI 绕不过去。

**覆盖两条写路径，不是一条**：`style` 只有两个入口——新建时的 `novel_init`，和旧项目的 `novel_amend`（零归档章、`style === undefined`）。只堵前者等于留后门：AI 可以对旧项目调 amend 直接设风格，完全不经过确认（C12）。两条路径共用同一个确认函数与同一套七态返回。

**为什么单独成包**：WP8 用 `required + enum` 保证值**合法**，保证不了值**是用户选的**。`ask_user_question` 虽然已在预设里（`presets/novel-write-engine.patch.yml` 的 `tool-ask-user`），但「AI 什么时候调」靠它自觉——那是文字约束，不是门控。本包把确认从「提示 AI 去问」改成「插件自己问」，并因此改 `novel_init` 的阻塞语义，属于契约变更，与风格包是两个风险面，故不并入 WP8。

**文件**：`src/tools/index.ts`（`novel_init` 参数与 handler、`UserQuestionsLike` 与 options 字段）、`src/index.ts`（`resolveUserQuestions`）、`tests/0217-confirm.spec.ts`、`docs/tools.md`、`src/client/panel.ts`（教程弹框）

**变更**：

1. **参数**：`novel_init` 增 `confirm?: boolean`，**默认 `true`**。默认 true 是因为主场景是人在会话里开书；脚本、CI、子代理显式传 `false`。
2. **取服务**：复刻 `resolveWorkingDirectory` 的模式（`src/index.ts:92-100`）——`src/index.ts` 加一个 `resolveUserQuestions()`，内部 `ctx.get('userQuestions')` 懒读、**每次调用重新取**；`WorkingDirectoryOptions`（`src/tools/index.ts:67`）旁加同构的 `UserQuestionsLike` 与 `resolveUserQuestions?` 字段。**不用 `optional.inject`**：`userQuestions` 是可缺席依赖，而 inject 在服务缺席时根本不执行回调——把 `novel_init` 的注册放进去，等于在没装提问服务的宿主里让这个工具**静默消失**。
3. **调用点**：`novel_init` 的**第一行**，在任何 `mkdir` 与写盘之前。问一个问题：

```ts
{
  id: 'init-confirm',
  header: '确认开书参数',
  question: `题材：${genre}\n平台：${platform}\n字数：${wordsPerChapter[0]}–${wordsPerChapter[1]}\n对白：${dialogueRatio[0]}–${dialogueRatio[1]}\n风格：${styleLabel}\n\n这五项创建后不可更改，确认吗？`,
  options: [{ label: '就这个' }, { label: '我要改' }],
}
```

**只问一个确认问题**，不把 genre/platform/style 拆成三个选择器。理由：主路径一次点击零摩擦；改选走「我要改 → 工具拒绝 → AI 重新询问 → 带新参数重调」。拆成多问题会让每次开书弹 4–5 个控件，反而劝退。

4. **迁移路径**：`novel_amend` 同样增 `confirm?: boolean`（默认 `true`），但门控**只在补丁使 `style` 从 `undefined` 变为某值**时触发——普通 amend 不问，不给日常修复加噪音。判定放在工具层（`projectPatchDelta` 之后、`narrow` 之前就能看出），**不能塞进 `amendProblems`**：语义闸只回答「能不能设」，确认必须发生在写盘之前，且 `amendProblems` 拿不到 `exec`。问题体换成迁移版本：

```ts
{
  id: 'style-migrate-confirm',
  header: '确认启用文风',
  question: `这本书建于 ${created_at}，还没有文风。\n风格：${styleLabel}\n\n风格一旦设定不可更改，确认吗？`,
  options: [{ label: '就这个' }, { label: '我要改' }],
}
```

5. **七态返回**（新增 `confirmation` 字段，不破坏现有调用方）：

| 结果               | 触发                                        | `confirmation`                | 是否创建项目 |
| ------------------ | ------------------------------------------- | ----------------------------- | ------------ |
| 用户选「就这个」   | `ask()` 正常返回                            | `'confirmed'`                 | 是           |
| 用户选「我要改」   | 同上，`answers[0].selected[0] === '我要改'` | 拒绝：`CONFIRMATION_REJECTED` | **否**       |
| 无 answerer        | 抛 `NO_PROVIDER`                            | `'skipped:no-provider'`       | 是（降级）   |
| 子代理调用         | 抛 `DELEGATED_CALLER`                       | `'skipped:delegated'`         | 是（降级）   |
| agent 非 live 实例 | 抛 `CALLER_NOT_LIVE`                        | `'skipped:not-live'`          | 是（降级）   |
| 调用方取消         | 抛 `ASK_ABORTED`                            | 拒绝：`CONFIRMATION_ABORTED`  | **否**       |
| `confirm: false`   | 显式传参                                    | `'skipped:disabled'`          | 是           |

实际调用形如 `ask({ questions: [{ id: 'init-confirm', header, question, options }], agent: exec.agent, signal: exec.signal })`，返回 `{ answers: [{ id, selected: string[], custom?: string }] }`。**四种错误码都是 `UserQuestionError`，靠 `code` 区分，不能靠 `instanceof` 猜**——`NO_PROVIDER` / `DELEGATED_CALLER` / `CALLER_NOT_LIVE` 降级放行，`ASK_ABORTED` 中止。

`CONFIRMATION_REJECTED` 的提示必须告诉 AI 下一步：**「用户要求修改。请逐个询问题材（12 选 1）、平台（4 选 1）、字数区间、对白比区间、风格（8 选 1 或不用），拿到明确答复后带新参数重新调用。」** 这句话是让「我要改」不变成死路的关键。

6. **降级不是静默**：`skipped:*` 四种情况都在返回里带 `confirmation` 与一行 `note`，`novel_status` 的项目块一并显示。降级本身是对的（子代理确实不能弹窗），但用户必须能看出「这次开书没经过确认」。
7. **`novel_archive` 不加确认**：归档错了只影响一章且 `novel_reopen` 能回退；init 错了要重建整个项目。风险不对称，不为对称给每章加一次点击。这条写进 §8 观察项。

**兼容**：`confirm` 缺省 true 会让现有测试都走 ask 路径——但测试环境无 answerer，返回 `skipped:no-provider` 后照常创建，不阻塞。`novel_amend` 的 `confirm` 只在 `style` 从 `undefined` 变值时才有意义，普通 amend 完全不受影响。新增测试必须显式 mock answerer 才能覆盖 confirmed / rejected。

**验收**：`tests/0217-confirm.spec.ts` 12 条——init 路径 9 条：confirmed 创建成功；rejected 不落盘且返回 `CONFIRMATION_REJECTED`；`confirm:false` 完全不调用 ask；`NO_PROVIDER` 降级；`DELEGATED_CALLER` 降级；`CALLER_NOT_LIVE` 降级；`ASK_ABORTED` 中止且**目标目录不存在**；ask 严格在首次写盘之前（mock 断言调用顺序）；`confirmation` 字段出现在 `novel_status`。amend 路径 3 条：迁移 amend 触发 ask 且 confirmed 后落盘；迁移 amend 被 rejected 后 `novel.yaml` 字节不变（不是「改了一半」）；普通 amend（不带 `style`）完全不调用 ask。

**风险**：用户不在电脑前时工具一直挂起——`ask()` 没有超时参数，超时只在 `askTimed()` 里（本包不用）。缓解：`confirm: false` 逃生口 + 文档写明「AI 会等」；将来要超时得改用 `askTimed`，那是独立决策，不在本包。

### 7.3 回滚

- WP1–WP5 按文件回滚，每 WP 一个独立提交面（本轮不提交，仅作为执行时的切分）。

### 7.4 如果排期必须压缩

**切法只有一条**：WP4 + WP5（存储与面板，6.5 人日）可以后移，因为它们不改契约、只修崩溃与可见性；**WP6–WP10 不能拆**——只发 schema 不发规则，等于给用户一个「选了没用」的开关，比不发更糟。**WP13 也不能后移**：WP8 把 `style` 做成不可变却不加确认，等于把「AI 可能替用户选错且永远改不了」写进契约，两者必须在同一个 release 里落地。

