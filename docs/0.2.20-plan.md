# 0.2.20 迭代方案：从「一章能过」到「一本能写」

> **结论先行**：0.2.19 证明了门控、评分、账本能把**一章**管住；但在真实长篇里，有三件事会让它从「有用」变成「不能用」——① 任务书随章数爆炸（58 章 P6 已 28 万字符，600 章 103 万字符，宿主裁剪阈值只有 8192 字符）；② 13 道门里有几道名义存在、实际拦不住（PG-10 只拦重复段落、13 项自查缺答默认 pass、PG-08 的「已修复」可以引用没改过的旧句）；③ 规则对真实中文稿误伤（引号、段长、落款空格、主语排比、顿号列举、跨段对白）。0.2.20 只做这三件事，并把它们写成可复跑的数字门禁。
>
> **状态**：方案定稿 v2。三项决策（D1 引号 / D2 跨章分级 / D3 段长）已按推荐锁定，不再留待拍板。本轮只读源码与文档、只在 `/tmp` 跑探针，**没有修改任何项目文件**，没有 commit/push/tag/publish。
> **上一版**：0.2.19（npm `latest`，commit `0b1b2c6`）。

## 0. 一页纸

### 0.1 这一版解决什么

| 问题 | 真实后果 | 0.2.20 的目标 |
| --- | --- | --- |
| 任务书体积随章数线性增长 | 58 章 P6 已 281,049 字符；600 章 1,033,493 字符。宿主压缩时的工具结果预算是 8,192 字符（头 4096 + 尾 1024）→ 压缩后只剩头尾，而回执写着 `complete: true` | 任意章数下，**每份任务书 ≤ 8,192 字符**；省略什么、去哪取，写在回执里 |
| 读模型每次全量重算 | 600 章：`status` 1.06s、`report` 0.92s、`doctor` 1.11s、每个面板分区 0.44–0.55s；`journal` 15.7MB 每次全解析 | 600 章 `status` ≤ 150ms、`report` ≤ 300ms、面板单分区 ≤ 120ms |
| 门禁「说了等于没说」 | PG-10 只拦 `DUPLICATE_PARAGRAPH`；13 项自查 8 行缺答仍 pass；PG-08 可用旧句冒充修复证据；`amend` 可静默删掉 worldbook 条目 | 每条门禁能指出「拦了什么、依据是什么」；做不到就降级成 honest advisory，不假装通过 |
| 规则误伤真实稿 | 真实 58 章稿：`ILLEGAL_QUOTE ×12` 拒稿、`LONG_PARAGRAPH ×9`、`PUNCT_STANDARD` 6 条里 4 条是作者有意排版 | 真实段落反例集 50 段，误报 0；规则口径可解释、可关、可迁移 |
| 文档与面板把用户挡在门外 | README 的 `novel_init` 示例**缺必填 `style`**，照抄第一步就 `ENGINE_SCHEMA_INVALID`；面板切项目失败会永久停在骨架屏；15 处文档与代码口径不一致 | 黄金路径示例可原样执行；面板状态机可恢复；文档数字由门禁生成 |

### 0.2 三个可验收的数字

1. **上下文**：600 章夹具上，P1–P8 七份任务书**各自 ≤ 8,192 字符**（当前 P1 80,005 / P6 1,033,493）。
2. **读模型**：600 章夹具上 `status` p95 ≤ 150ms、`report` ≤ 300ms、`panelSection` ≤ 120ms（当前 1,058 / 916 / 443ms）。
3. **误报**：50 段真实段落反例集上，新规则命中数 = 0（当前 `PARALLEL_RUN`、`ENUMERATION`、`PUNCT_STANDARD` 都会误报，见 §1.4）。

### 0.3 不做

- 不加工具、不加阶段、不加门控编号（仍是 28 工具 / 9 阶段 / 13 门 / 15 维 / 150 分）。
- 不改 `SCHEMA_VERSION`（保持 1）；新字段全部可选。
- 不做英文、不做多用户、不做面板视觉重做、不做 SQLite。
- 不把「语义判断」升级成机检——那需要另一个模型，不是这一版的事。
- 不修 0.2.19 已发布的 tarball 里的旧 README（npm 不允许重发同版本）；0.2.20 重发时自然带上。

### 0.4 与 0.2.19 的关系

0.2.19 的交付面（13 项自查、机检度、`scoring_basis`）在 0.2.20 里**保留**，但有五处口径变更：

- `self_check` 的缺答行为从「记一句 note 仍 pass」改成「`na`，且归档前必须清空」；
- `context_meta.complete` 从常量 `true` 变成真实布尔，并新增 `budget`/`omitted`/`fetch`；
- `ILLEGAL_QUOTE` 从「只许英文直引号」改成「与项目声明的引号风格一致、且成对」（D1）；
- `TIME_REGRESSION` 从 advisory 升 blocker（D2）；
- `LONG_PARAGRAPH` 从「含标点 90 单位」改成「CJK 字数（标点不计）150」（D3）。

### 0.5 三项已定决策（实施时不再讨论）

#### D1 · 引号策略：项目声明式（选 B）

项目文档 `novel.yaml` 新增可选字段：

```yaml
quotes: ascii   # 缺省值；可选 "curly"
```

| `quotes` | 允许 | 拦截（`ILLEGAL_QUOTE`，blocker） |
| --- | --- | --- |
| `ascii`（缺省） | 半角 `"` | `“”`、`「」`、`『』` |
| `curly` | `“”`、`「」`、`『』` | 半角 `"` |

补充语义：

- **同段混用**：一段里同时出现 ASCII 引号与中文/直角引号，无论声明哪种风格，一律 blocker（`ILLEGAL_QUOTE`）。
- **成对检查**（`QUOTE_UNBALANCED`，blocker）按声明风格判定：ASCII 模式沿用「本段计数必须为偶数」；curly 模式改**跨段状态机**——段首 `“`/`「`/`『` 记 pending，续段再次以 `“` 开头视为继续（中文多段引用的合法写法），到章末仍未闭合才报。
- **PG-04 提示语**按项目风格生成，不再固定写「must use ASCII double quotes」。
- **P3 任务书**里那句「中文弯引号都是 blocker」改成占位符 `{{quotes_rule}}`，由项目设置渲染；P6 任务书同步。
- **老项目零变化**：缺省 `ascii`，与 0.2.19 行为逐字节相同。
- **入口**：`novel_init` 增加可选参数 `quotes`；`novel_amend` 可改一次并写 journal（`quotes_changed`）；已归档章不回算。
- **不静默改正文**：不做「自动把 `“”` 规范化为 `"`」的 C 方案——那会改作者的文字。

为什么选 B：真实模型写中文引号的概率极高（0.2.19 实测 `ILLEGAL_QUOTE ×12` 拒稿，`agnes-3.0` 连续 10 次没过），而「只许英文直引号」本质是把排版偏好伪装成正确性。B 把选择权交给作者，同时保留「混用/不成对」这个真正的错误。

#### D2 · PG-10 分级：只升时间倒退（选 B）

| 跨章规则 | 0.2.20 默认 | `strict_cross: true` 时 |
| --- | --- | --- |
| `DUPLICATE_PARAGRAPH` | blocker（现状） | blocker |
| `TIME_REGRESSION` | **blocker（新）** | blocker |
| `FORESHADOW_DORMANT` | advisory | advisory |
| `FS_REVISITED_TOO_SOON` | advisory | advisory |
| `RESOURCE_MISMATCH` | advisory | **blocker** |
| `LOCKED_DETAIL_DRIFT` | advisory | **blocker** |

实现要求：

- 严重度**只有一个 owner**：`RuleContext.strictCross?: boolean` + 一个 `crossSeverity(code)` helper；`TIME_REGRESSION` 直接返回 blocker，`RESOURCE_MISMATCH` / `LOCKED_DETAIL_DRIFT` 返回 `ctx.strictCross ? 'blocker' : 'advisory'`。
- **P6 check 与 PG-10 必须同源**：`runCheck` 与 `runRules` 都传同一个 `strictCross`，不允许出现「check 说 advisory、归档说 blocker」。
- 项目字段 `strict_cross: boolean`（缺省 false），可在 `novel_amend` 里切换；回执说明本次拦了哪几条、依据是什么。

为什么只升 `TIME_REGRESSION`：时间倒退是硬事实（新事件早于已发生事件），可被 timeline 直接证明；资源对账依赖口语数解析，而 `一亿三千万` 这类还没有解析（见 §8 风险），升 blocker 会制造新的误伤。

#### D3 · 段长口径：CJK 字数 + 150（选 C）

- `LONG_PARAGRAPH` 的计数单位从「CJK + 英文词 + 数字 + 标点」改成 **CJK 字数（标点不计）**。
- 规则包默认值 `format.paragraph_max_words` 从 `90` 改为 `150`；键名不变，语义在 `docs` 与规则包注释里写清。
- `WordMetrics.paragraph_max_words`（`novel_word_count` 回执里的指标）同步改成 CJK 口径，避免「统计说 95、规则说 78」。
- 已归档章不回算；新章重跑 P6 会看到 `LONG_PARAGRAPH` 命中大幅下降，CHANGELOG 明说。

为什么：现状的 90 个单位把标点算进去，真实稿里 80 个汉字 + 15 个标点就超限（实测 `LONG_PARAGRAPH ×9`），等价于「要求作者把段写短于 75 个汉字」。150 个汉字的硬上限与网文排版习惯一致，同时仍能拦住真正的大段。

## 1. 事实基线（本轮实测）

测量环境：Node 24.22.3 / WSL / Windows 盘挂载 / 同一台机器；数据取自一个真实连载项目（书名、路径与人物按隐私门禁不写入仓库；58 归档章 / 65 个正文文件 / 194,000 字 / journal 2,266 行 1.57MB）与由它派生的 600 章夹具（时间线扩到 4,800 条，其余同比）。探针在临时目录，未写入项目。

两点读数：

- **只有 P6 吃全量台账**，其余阶段已经按「最近几章」开窗；但 P1/P2/P3/P8 仍带**全部伏笔台账**（真实项目里 136KB，是 P1 的主体），所以它们会随书增长，只是慢。

**宿主侧的硬约束**：`@deepseek-ai/dsh-compaction-tool-result-pruner` 在压缩时把**任何超过 8,192 字符**的工具结果剪成 `head 4096 + 标记 + tail 1024`（`packages/compaction/compaction-tool-result-pruner/src/config.ts:9-13`，本机 DSH checkout 实测）。预设 `presets/novel-write-engine.patch.yml:48` 正是这组默认值，且该插件**没有按工具名豁免的配置项**。

> 事实：P6 任务书是阈值的 34 倍（58 章）到 126 倍（600 章）。无论截断发生在哪一层，模型看到的都不是它以为拿到的台账；而 `context_meta.complete` 恒为 `true`（`src/engine/context.ts:530,549`），回执在替这个错觉背书。

### 1.2 长书：读模型延迟

| 操作 | 58 章 | 600 章 | 说明 |
| --- | ---: | ---: | --- |
| `getStatus` | 230ms | 1,058ms | 每次直接 `readJournal`（`src/engine/service.ts:3263`） |
| `report` | 281ms | 916ms | 全量章节摘要 + journal |
| `doctor` | 489ms | 1,107ms | 同上 |
| `panelBundle` | 221ms | 555ms | 51.6KB 载荷 |

| `queryState chapters` | 169ms | 276ms | 5.6KB |

冷启动与热调用几乎相同 → 这些路径**没有有效缓存**；`journalCache` 只服务 `journalBlocking`，`statusFor` 绕过它自己再解析一遍。真实项目 journal 增长曲线是每章约 40 行（pending + committed + aborted），600 章约 15MB；照此速度，1,000 章时单次 `status` 会到 2 秒以上。

### 2.3 红测纪律（0.2.20 的测试契约）

每个行为改动都必须走完四步，缺一步视为未完成：

1. **先红**：新增或改写测试，先跑，记录命令与失败输出；失败原因必须是「目标行为不对」，不是语法错误、缺导出、夹具写错。
2. **再绿**：最小实现让该测试转绿，再跑同文件全套。
3. **能变红**：同一条测试在旧实现上必须红。做不到，说明它没测到行为，重写而不是留着。
4. **边界三件套**：正例（该报的报）、反例（不该报的不报）、误报例（以真实稿为蓝本的去标识化改写，保留句式与标点，不直接入库未发表正文）。

补充规则：

- 旧测试固化了错误行为时（如 `0219-selfcheck-doc:160-164` 把「缺答 pass」写成期望），改写它并在实现日志注明「旧期望是错的」——不许为了让实现通过而放宽断言。
- 规则类改动必须同时进 50 段反例集；只跑合成短串不算验证。
- 性能与体积类改动必须由 `check:scale` 产出数字，不许手写「约」。
- 任何「已修好」的结论，都要附一条能证伪它的命令。

### WP4 读模型（4 人日）

**目标**：§2.1 的延迟预算。

做法：

1. **journal 增量缓存**：`readJournal` 单入口，缓存 `{path, size, mtimeMs, records, rows, malformed, offset}`；追加后只解析新增字节。`statusFor` / `report` / `doctor` / `auditHistory` 全部走同一入口（当前 `service.ts:3263` 绕过缓存）。
2. **章节索引 sidecar**：`state/index.json`（派生，可重建）只存 `num/title/word_count/score/status/scene_type/content_hash/updated_at`；每次写 `chapters.yaml` 的事务同步写它；读取时校验 `chapters.yaml` 的 `(size, mtime)` 与 sidecar 记录，不一致即重建。`status`/`panelChapters`/`report.effort` 先读 sidecar，只有需要 `summary` 时读全量。
3. **快照复用**：`panelSection` 的每个分区共享同一次 `loadSnapshot`（当前每区各自读账本）；section 缓存键加入 `revision + journal size`。
4. **auditHistory 反向分页**：从文件尾按行切，不解析全量；`total` 用 sidecar 计数。
5. **doctor 的 journal 计数**：只在检测到 pending 时读尾窗口，全量扫描仅 `doctor` 显式 `deep:true`。
6. **质量分区**：`quality` section 当前对每个归档章串行 `await readDoc`（600 章 = 600 次读+解析）。改成 `Promise.all` 限并发 8，且只聚合最近 120 章做维度均值，超过部分注明 `window: 120`；`panelReviewKey` 的逐个 `stat` 一并进缓存。
7. **便宜 ETag**：bundle 现在先完整构建再算 ETag，304 只省网络。改成用 `revision + journal(size,mtime)` 生成 ETag 并在构建前判 304。
