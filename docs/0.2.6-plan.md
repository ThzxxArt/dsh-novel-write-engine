# 0.2.6 迭代方案：证据配对、实体锚点与书籍数据

> 基线：`448447d`（0.2.5）。本文件是下一轮实施方案，不包含代码改动；文中行号对应此基线。
> 审计方式：逐文件完整读取 `src/` 60 个 TS（29,454 行）、`docs/` + `briefs/` + `skills/` 30 个文件（4,471 行，截图除外）、`tests/` 84 个 TS（27,000 行），另只读核对真实项目 `1971从偷渡港岛开始`。

## 1. 结论

0.2.6 不应只做“再加几个面板字段”。当前同时存在三类问题：

1. **证据判定正确性和可解释性不足**：`semantic.ts` 不做词面相似，但长引文一旦跨段，会把覆盖到的所有句子占为“已用”，后文不同段落的证据被判 `same_sentence`；错误只带第一条，且配对信息不落盘。
2. **实体名称与正文检索串绑死**：PG-05 和 `state-delta.ts` 对 `new_elements`/world 新实体使用 `text.includes(name)`。真实第 4 章日志已出现 `summary lists new location "城寨六婶家" but the manuscript never mentions it`，调用方只能回 P5 把台账名塞进正文。
3. **面板没有展示“书本身”**：当前只有标题/字数/章数/均分、卷/章计数、世界观计数、质量条和最近活动；蓝图身份、角色与关系、地点/势力/规则、伏笔/时间线、节奏、15 维质量、逐章 effort、当前章卡、state_errors、pending 都没有进入 wire。更严重的是已有数据也存在假绿/错标：`pending` 已计算但 `projectSummary` 没复制，`revisionLabel` 用的是全局 revision，`近十均分` 用的是全书均分。

0.2.6 的定位：**把“证据、台账锚点、书籍数据”从“能跑”变成“可解释、可验证、可读”**，不重写引擎、不新增工具/命令/阶段、不放宽任何门控。

## 2. 审计发现（必须进入方案的证据）

### 2.1 真实第 4 章

- `state/journal.jsonl:298`：`archiveChapter` 被拒绝，原因逐字为 `state_delta is incomplete: summary lists new location "城寨六婶家" but the manuscript never mentions it`。
- `state/world.yaml:31-37`：`城寨六婶家` 已作为 location 落账，描述是唐楼三楼尾房；正文实际写的是“三楼尾房/楼梯底三楼”这类场景名。
- 第 4 章最终为了过归档，在正文加了“可读登记名 + 动作”式的补写（`chapters/chapter-004.md:59`）；具体正文不复制。这不是作者想写的句子，是台账检索串污染正文的直接证据。
- 语义失败提交没有写入 check（submission error 不落 check），`history/checks` 只保留 pass/fail 结果；因此用户报告的具体两条引文无法从项目持久化数据中复原。0.2.6 的回归必须同时使用**真实项目只读探针**和**同形合成文本**，不能把未持久化的失败当成已证实根因。

### 2.2 语义证据

`src/engine/semantic.ts` 只有三种原语：

- `text.indexOf(quote)` 做逐字定位（268-273）；
- 字符区间相交（292）；
- 覆盖句子的索引集合（297-311）。

它**没有**词面相似判断，所以“不同段落只共享几个词”在当前实现里本身不会被判 overlap。可达的误判路径是：

1. 先接受的证据 A 跨段/跨句，覆盖了段落 P 的句子；后文证据 B 落在 P 的另一段，因 A 已占用 P 的句子而被判 `same_sentence`——用户看到的是“不同段落”，机制却是“长证据吃掉了后文句子”。
2. `sentenceSpans` 只认 `。！？!?` 和换行，不认 `…`/英文句点；而 `domain/text.ts` 的 `splitSentences` 认 `…+` 和英文句点。按 P6 文档写出的“不同句子”可能被引擎归入同一个 span。
3. `CheckSubmissionError` 只把第一条非 pass/fail 渲染进 message/hint（63-77），`items` 只在当次工具错误里出现；`conflict_with` 不写 check、不写 journal，失败后无法回看“谁和谁、哪一段、重叠多少字”。
4. 当前 `overlap` 的拒绝条件是任意字符区间相交，没有重叠长度/比例阈值，也没有把重叠片段返回。对长引文，这会把“共享一小段真实原文”与“整段重复取材”混为一谈。

因此 0.2.6 的核心不是“加一个相似度阈值”本身，而是：

- 统一句子边界（单一 owner）；
- 把结果从“批次 + 第一项”改为“逐项 + 配对”；
- 区分 exact duplicate / same sentence / meaningful interval overlap / 仅词面相邻；
- 让失败证据可回看。

## 4. 契约设计

### 4.1 语义证据

新增（均为 additive，check schema_version 不变）：

```ts
type SemanticConflictKind = 'duplicate' | 'same_sentence' | 'interval_overlap'

interface SemanticConflict {
  kind: SemanticConflictKind
  other_id: string
  /** 仅在 interval_overlap 出现；逐字截取，最多 120 字 */
  overlap_text?: string
  overlap_chars?: number
  /** overlap_chars / min(quoteA, quoteB)，0..1 */
  overlap_ratio?: number
  paragraphs?: number[]
  /** 仅在 same_sentence 出现 */
  sentence?: { id: number; text: string; paragraph: number }
}

interface SemanticItemResult {
  // ...现有字段
  conflicts?: SemanticConflict[]
}
```

`CheckSubmissionError` 增加：

```ts
readonly conflicts: SemanticConflict[]
readonly blocking: BlockingItem[]   // 逐条，不只第一条
```

判定规则：

1. 用 `domain/text.ts` 的 `splitSentences` 作为唯一句子切分 owner；段落边界继续由 `splitParagraphs` 负责，删除 `semantic.ts` 的私有句切分逻辑或改为调用同一函数。
2. 同一 normalized quote 完全重复 → `duplicate`。
3. 两条证据覆盖同一 sentence id → `same_sentence`；即使两个子串不相交也拒绝（这是“同一句原话”的真实重复）。
4. 字符区间相交时：
   - 一条包含另一条 → `interval_overlap`（containment）；
   - 否则计算 `overlap_chars / min(lenA, lenB)`；只有 `overlap_chars >= max(8, ceil(0.5 * minLen))` 才拒绝；
   - 低于阈值仅算“共享一小段原文”，不拒绝，不写 conflict；
   - `overlap_text` 一律取交集原文，返回段落/比例。
5. 不同段落、没有字符区间交集、没有同句复用 → **必须通过**，不因共享“秤/何九”等词拒绝。
6. 每条证据独立评估；失败的证据不占用 accepted span，后面的证据不得被前一条失败级联污染。只把 pass/fail 且被接受的区间写入 `spans`。
7. `boundary` 仅在没有可映射句子且不是 not_found/duplicate 时产生；不再用 `conflict_with: id` 的兜底。
8. `nearest` 只在 `not_found` 返回，增加相似度阈值；低于阈值不返回，避免用“共享常用词”误导模型。
9. `CheckSubmissionError` 的 message 必须列出所有配对摘要（最多 5 条，附带 item id、段落、重叠字数）；`items` 仍完整。aborted journal 写入 `blocking` 的紧凑配对摘要（id、kind、overlap_chars），不写正文全文。

测试必须覆盖：

- 两个不同段落、共享 3–5 个词 → pass；
- 同一句不同子串 → `same_sentence`，带 sentence text/paragraph；
- 完全重复 → `duplicate`；
- 长跨段证据结束于后文段落之外时，后文独立段落不因 A 的覆盖集误杀 B；若 A 的引文实际包含 B 的句子，仍按第 3 条同句复用拒绝；
- 真正包含/高比例重叠 → `interval_overlap`，带 overlap_text/chars/ratio；
- 4 真实 + 1 编造 → 只有 `not_found`，无 cascade；
- 工具/命令错误可看到所有配对，check 文档仍不因 submission 写入；
- 真实 r0076 形通过，r0075 形 POV 仍只 `not_found`。

### 4.2 实体锚点

新增字段（additive）：

```ts
interface ChapterSummary {
  new_elements: { locations: string[]; abilities: string[]; artifacts: string[] }
  new_element_anchors?: {
    locations?: Record<string, string[]>
    abilities?: Record<string, string[]>
    artifacts?: Record<string, string[]>
  }
}
```

`WorldDocument` 的实体增加：

```ts
interface WorldLocation {
  name: string
  /** 0.2.6 新增；旧文档没有该字段 */
  anchors?: string[]
  // ...
}
```

`world.abilities/artifacts/factions/rules` 的条目同样可有 `anchors?: string[]`（当前是 unknown[]，只做结构校验，不强制类型收窄）。

关键决定：**章级锚点的唯一输入 owner 是 `summary.new_element_anchors`**；world delta 不再增加第二套 anchor 输入。理由：

- PG-05 在 P3/P5 就要判定，此时还没有 `state_delta`；
- 0.2.5 的 summary-only 已允许只改摘要，不动正文；
- world 台账只保存已经确认过的 anchors，供后续报告/面板展示；
- 避免 `summary` 与 `world delta` 两个真源再次冲突。

规则：

- 每个 name 必须仍在 `new_elements` 对应数组中；ANCHOR_MAP 出现未知 name → schema error。
- anchors 是字符串数组，去空白、去重，长度 2..120，最多 8 个；不允许空字符串。
- 有 anchors：至少一个 anchor 在正文逐字出现；没有一个命中 → `ENGINE_DELTA_UNVERIFIED` / PG-05，错误列出 name、尝试过的 anchors、最接近的段落（可选）。
- 无 anchors：保留旧规则，name 必须逐字出现；错误 hint 明确“提供 new_element_anchors，或在正文写入 name”。
- 只在“新建/归一化为新建”的 world 实体上要求正文命中；已有实体的 updated/no_change 不因正文没有规范名而失败。
- 持久化：新建/更新时把 anchors 合并去重写入 world entity；旧 world 没有 anchors 保持原样，不迁移。
- `entity-anchors.ts` 是唯一 helper，PG-05 与 state-delta 共同调用；禁止再写 `text.includes(name)` 的 world 分支。

测试：

- `城寨六婶家` + `["三楼尾房"]`：P3/P5 PG-05 和 P8 archive 均通过，正文不需要出现规范名；
- 同名但 anchors 无命中 → 拒绝，错误可操作；
- 无 anchors 且正文无 name → 拒绝（旧规则保留）；
- anchors 持久化到 `state/world.yaml`，report/panel 可见；
- 旧项目 world 无 anchors 可读；旧 summary 无 anchors 仍按 name 判定；
- 真实第 4 章同形合成文本通过，不需要 P5 正文补写。

- **pipeline recovery 的破坏性**：必须从 backup/显式文档恢复，不能绕过 journal hash；先做恢复演练，不删除证据。
