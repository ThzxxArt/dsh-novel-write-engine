## 4. 本轮发现并修复的问题

### P1-1 · 旧规则包仍会出新码与新的 S13 触发（兼容性承诺不成立）

- **根因**：11 个实现里 9 个在入口读 `selfcheckOf(ctx)`，`quoteUnbalanced` 与 `separatorOnlyParagraph` 漏了这一步。前者直接产出新码，后者把「整段 `……`」并入既有 `SCENE_SEPARATOR`（blocker）。
- **影响**：任何 0.2.18 项目只要包没有 `selfcheck` 块，引号未配对会被新 blocker 挡下；整段省略号也会突然从「允许」变「blocker」。`docs/selfcheck.md`、CHANGELOG、验收 §4 都写着相反的话。
- **修**：`src/rules/selfcheck.ts:518`（引号）与 `:741`（S13 扩展）各加一行闸门。
- **红证据**：新增用例「produces none of the eleven codes on a pre-0.2.19 pack, trigger by trigger」，修前失败在 `{ code: 'QUOTE_UNBALANCED', legacy: true }`；修后 79 项全绿。

### P1-2 · 两个新 blocker 不在 PG-04 里（「blocker」只在 P6 才生效）

- **根因**：`src/engine/gates.ts` 的 PG-04 规则表硬编码 8 个码，方案 §12 与验收 §4 都声称新码「纳入 PG-04」，代码没加。
- **影响**：带半角标点/未配对引号的草稿能过 P3、消耗一整轮 P4 评审与 P5 修订，最后才在 P6 被挡；若只看门控回执，模型永远不知道是哪个 gate 拦的。
- **修**：PG-04 规则表补 `PUNCT_STANDARD`、`QUOTE_UNBALANCED`（`src/engine/gates.ts:192`）。
- **红证据**：新增 3 条用例（半角标点 / 未配对引号 / 旧包放行），修前前两条拿到 `null`（草稿被接受），修后分别报 `PG-04 … PUNCT_STANDARD` 与 `PG-04 … QUOTE_UNBALANCED`，旧包仍 `resolves`。

### P2-1 · `legacy_chapters` 漏掉没有 `archived_at` 的旧行

- **根因**：`src/engine/insight.ts` 的 `legacyScoring` 先按 `record.archived_at` 非空过滤，但 0.2.18 早期的行没有这个字段；同一个函数的 `effortChapters` 已经用事务日志回填并给出警告。
- **影响**：真实 57 章书的报告写「legacy_chapters: [2…57]」，把第 1 章漏了——那正是最早按自评口径评审的一章。
- **修**：去掉该过滤（`ChapterRecord` 只可能来自归档；`reopen` 会恢复账本前像），保留 `scoring_basis !== 'machine'`。
- **红证据**：新增用例「names a legacy row that predates the archived_at field too」，修前 `undefined`，修后 `[1]`。

### P2-2 · 一条测试的名字与内容不符，一条防回归用例空转

- `refuses a pass that contradicts a machine finding` 原先**没有提交任何 `self_check`**，只断言引擎自己的行判定，服务端「不得填 pass」的分支无人覆盖。已改为先提交撒谎的 `SC-FORMULA: pass` 断言被拒（`cannot be marked pass`），再跑一次确认该行 fail。
- 「stays entirely silent when the pack has no selfcheck block」原先只用 `CLEAN` 基线——那条文本本来就不触发任何规则，因此 P1-1 的漏洞一路绿灯。已改为 11 条触发串逐条断言。
- 同类：`0219-selfcheck-doc` 的 `atP6` 与 `readyToArchive` 都会传 `total`，机检度生效后必然不符；已改为省略 `total`（引擎实算），与真实调用方口径一致。

### P3-1 · `punctStandard` 里的死分支（覆盖率与文档同时失真）

- **根因**：`touchesChinese` 已在前面 `continue`，后面的「两侧都是拉丁/数字则豁免」永远不可达。文档 S9 把豁免归功于它，实际是「两侧都无中文」在起作用。
- **影响**：`src/rules/selfcheck.ts` 分支覆盖 93.96%，低于方案 DoD 第 7 条的 95；注释误导后续维护者。
- **修**：删除死分支与 `LATIN_OR_DIGIT` 常量，注释写清真正机制；补一条「模型行带引文」用例覆盖另一处未覆盖分支。
- **红证据**：删除前该分支在覆盖率报告中列为 uncovered（`586-593`）。修后 `src/rules/selfcheck.ts` 覆盖率 **100 / 95.04 / 100 / 100**，方案 DoD 第 7 条的「95×4」达标。

### P3-2 · 「全章」定位是可达性为零的陷阱（未修，记录）

`machineLocation` 在找不到段落时返回 `全章`，而 PG-07 只接受「第 N 段」。当前唯一会给 `R-W-09` 扣分的信号（字数低于项目下限）在 `PG-03` 之后不可能出现，所以这条路径**今天不可达**；若将来放宽字数门或允许改 `words_per_chapter`（现在不可变），它会变成一个无法自救的拒绝。已在 §9.3 记录，不在本轮改。

### 确认「不是缺陷」的 5 条

1. **D3**（`STYLE_PARAGRAPH_CHARS` 对 7 个包静默）：包上限 ≥ 全局 90 时，包要报的段落是 `LONG_PARAGRAPH` 已拦集合的子集，开火只会叠 advisory。判定修正成立。
2. **S13 复用 `SCENE_SEPARATOR`** 而不是新增一个码：一个判据一个 owner，读面与豁免都只认一个码。
3. **机检度覆盖模型声明**：这是 WP4 的定义，不是误伤；`adjusted[]` 保留了「你写的 / 引擎算的」。
4. **旧 check 文档带 `legacy_format` 字段**：0.2.18 的文档仍可读，字段不影响判定。
5. **`basisOf()` 只被测试与 `src/index.ts` 引用**：它是导出 API，不是生产死代码。

### 两条无法在本轮消除的取舍

1. `FRAME_REPEAT` 的句首规则依赖角色台账，无台账时真实稿 2.43%，超过 2% 红线（§9.2）。
2. `PUNCT_STANDARD` 会把「刻意的半角空格落款」判成 blocker（§9.1）；规则没错，但需要迁移指引。

### 文档级 · 验收与 CHANGELOG 的计数/标签漂移

见 §3，已按复算值修改 `docs/0.2.19-acceptance.md`（测试数、覆盖率、§2 夹具数、227 的标签、§4 的 PG-04 说明）与 CHANGELOG 的旧包承诺（现在成立）。

## 9. 发布风险与建议

### 9.1 重跑 P6 会挡住几章（最重要的发布风险）

- **4 章 / 6 段**：第 15、39、45、51 章；`QUOTE_UNBALANCED` 0 段。
- 逐段看：第 15 章 2 段是真正的半角 `?` 与半角引号；第 39/45/51 章 4 段是**用半角空格分隔的落款、字号、账目**（形如「店主 ○○○」「商号 ○○○ ○○○ 三十支」「某年某月某日 左手两指 某氏 未报」）。
- 判断：规则本身没错（它只管「两个汉字之间的半角空格」），但这 4 段是作者有意的排版，不是损坏。**建议**：发布说明里给出机械迁移——把分隔空格改成全角空格 `U+3000` 或改用顿号；只有整本书都不想改时才用 `exemptions: [PUNCT_STANDARD]` 整码关闭（会同时关掉半角标点检查）。
- 已归档的章不会自动重算，所以风险只在「重新 reopen 那 4 章并发版」时出现。

### 9.2 `FRAME_REPEAT` 的句首规则依赖角色台账

真实稿带台账 0.88%，不带台账 2.43%，超过方案 §17 的 2% 红线。新项目在 P1 之前没有 `characters.yaml`，**第一章可能偏多**。advisory 不阻塞归档，但会让第一章的自查卡出现 ×；建议在 P1 任务书里提示「先把本章出场人物写进 characters」，或接受第一章的这条 advisory。

### 9.3 机检度的实际作用面比文档小

`R-W-08` 的 6 个码里 5 个是 blocker、`R-W-10` 的 `TITLE_FORMAT` 也是 blocker，它们都会在 PG-04 先把正文挡下，所以**能走到评审的稿子在这两维几乎总是满分**；`R-W-09` 的字数信号被 PG-03 挡住，实际不可达。真正会动分的只有 `R-W-06`（短段）与 `R-W-07`（AI 腔/句式）。这不是缺陷，但发布说明不要把它写成「五维都会被扣分」。

### 9.4 传 `total` 的旧调用方会失败

0.2.18 的调用方若坚持自己算 `total`，在机检命中时会收到 `ENGINE_SCORE_MISMATCH`（回执同时给 `expected` 与 `machine_scores`）。迁移写明「省略 total，或按 P4 任务书的 `machine_scores` 复算」。这是本轮唯一会让既有调用方**报错**的接口行为变化。

### 9.5 模型能力波动

`agnes-3.0-flash` 本轮未能复现上一轮的六阶段一次通过：一半失败是免费额度 429，一半是它自己反复写「」引号（`ILLEGAL_QUOTE`，0.2.18 就会拒）。发布前若要保留「两个模型都通过」的说法，需要重跑并换证据。

### 9.6 发布前建议动作（按顺序）

1. 决定 §9.1 的 4 段处理方式（建议改稿，不改规则）。
2. 若要保留 3.0 的通过证据，重跑 `agnes-3.0-flash` 并更新 `docs/evidence/0.2.19/real-model-agnes-3.0-flash.md`。
3. 用最终树重跑一次 `test` 与 `test:coverage`（本轮已跑，若之后还改代码需再跑）。
4. commit → tag → publish 三步都**等我单独下指令**。
