# 0.2.20 复审轮：多维度代码与功能 review

> 范围：0.2.20 实施完成后的**第二轮**全量 review。目标不是「再过一遍测试」，而是找出
> 「每个单独调用都合法、连起来就错」的路径，以及「代码说的和做的不一致」的地方。
>
> 约定：先写会变红的测试再改代码；每条都记录**修复前的红灯证据**。未修复的条目在
> §5 单列，不混进「已修」。

## 1. 方法与分工

七个只读 reviewer 按层并行通读（rules / store / engine 数据层 / service 写半 / service 读半 /
tools+domain+client / 脚本与文档口径），我本人负责跨层不变量、写修复与验收。每个 reviewer
都被要求：给出 `file:line`、可复现的调用序列、最小修复，并区分「已确认」与「存疑」。

修复按文件所有权分给三个并行 fixer（client / rules / store），我保留
`service.ts`、`gates.ts`、`context.ts`、`insight.ts`、`schema.ts`、`tools/index.ts`、`book.ts`，
避免并发改同一文件。

## 2. 结论

0.2.20 的实施方向是对的，但**「引擎说的和做的不一致」还剩下三类**，本轮全部命中：

1. **回执不诚实**：窗口化只覆盖了 `novel_brief` 的「整行」维度。行内字段被截断（80 字上限、
   嵌套列表只留 2 条）不写回执，`complete` 仍为 `true`；`novel_state` / `novel_report` /
   `novel_audit` 的载荷在真实 58 章书上分别到 19.8 KB / 15.6 KB / 16.3 KB，超过宿主 8,192
   码点后**静默剪断**，没有任何 `complete` 标记；两阶段批量 `novel_brief` 一次返回 2.7 倍上限。
2. **「合法序列」能绕过门控**：一次字节不变的 `novel_revise` 可以关掉自己的 blocker；首次
   review 里 block 可以「生下来就是 fixed」；`summary-only` 修订后 `amend_issues` 可以把
   blocker 标成 fixed 而不改一个字；`novel_restore` 可以把已归档章从索引里删掉而不报错；
   归档后的 P1 brief（正是 `novel_status.next` 推荐的下一步）会让 `novel_reopen` 永久失败。
3. **配置项没有写入口**：`quotes` / `strict_cross` / `self_check_required` 三个 0.2.20 字段
   不在项目 schema 里，`novel_init {quotes:'curly'}` 会写出**引擎自己读不回来的项目**
   （`PROJECT_UNREADABLE unknown key "quotes"`，之后所有写都被拒）。这是本轮唯一的 P0。

另有并发与存储层的两个 P1：释放墓碑可以抢走仍然活着的锁（两个 writer 同时持锁），以及
补偿失败仍写 `aborted` 终态（下一次写在半恢复的项目上继续）。

- 偏差 6：`tests/0217-fixes.spec.ts`、`tests/0220-wp2.spec.ts`、`tests/engine-contract.spec.ts`、
