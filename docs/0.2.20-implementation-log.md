`vitest run tests/0220-brief-budget.spec.ts` → P4 `payload 10342 ... expected 10342 to be less than or equal to 8192`，P6 11,970、P8 15,318；`context_meta.complete` 仍是字面量 `true`、`version` 仍是 1。

### 根因（计划写错的地方）

计划的假设是「必需块本来就装得下，只要裁掉可选台账」。实测装不下，而且是**结构性的**：

| 阶段 | 静态任务书 | 静态字段 | 必需数据 | 合计 |
| --- | ---: | ---: | ---: | ---: |
| P4 | 3,551 | 1,297 | self_check 1,431 + machine 1,147 | 7,426（正文还没算） |
| P6 | 3,092 | 1,497 | review 1,385 + machine 757 + self_check 741 | 7,472 |
| P8 | 5,019 | 1,924 | check 4,127 | 11,070 |

所以「裁可选块」永远够不到 8,192。真正要做的是**降必需块的信息密度**，不是裁行。

### 已实现（全部不改公开契约）

- `content`（任务书）重写：P4 3,551 → 2,116、P6 3,092 → 2,168、P8 5,019 → 2,411 码点。删的是与 `fields`、`context` 重复的内容：十五维满分表移进 `fields.dimensions`（数据不再用散文重复）、P8 的最小 schema 只留 `fields.delta_rules.minimal_schema`（原来在 P8.md 里抄了一份）、P4 的锚点表压成两行。
- `compacted`：review / check / machine 超过阈值时换成**定位器**（码 + 段号 + 60 字摘录 + 计数），完整文档用 `novel_state` 取；`context_meta.compacted` 记 `{full, shown, why}`，`complete` 因此为 false（不假装完整）。
- `self_check` 只留 `id` + 12 字 `title`，去掉 `basis` 整列（1,431 → 741）；且只发 P3/P4（P6 不再重发，741 省掉）。
- 按阶段装填：`book_plan` / `scene_distribution` / `previous_ending` 只给 P1–P3、P5（判定阶段读自己的章卡）；P6/P8 不再带 `plan`（读的是要归档的 `summary`）；P4/P6/P8 不带计数口径字段（`word_count_policy` 等约 600 码点）。
- **正文从「豁免」改为「最后裁、按段裁」**：这是对 0.2.17 契约的明确反转，理由写在 `context.ts` 注释里——宿主超过 8,192 会按码点从中间剪断，模型读到半句话且**没有任何回执**；按段裁 + `omitted.text` + `fetch: novel_export` 至少让读者知道自己缺什么、怎么取。`budget.exempt` 现在是 `[]`。
- `briefBudgetFor` 改成**实测闭环**：算出预算 → 造一次真实 payload → 超了就按超出量收缩预算重建（最多 6 轮）。这个函数同时是 PG-01 复算 digest 的入口，所以 brief 与门禁不可能对窗口有不同理解。

### 找到的真实瓶颈（都不是"少读几次"能解决的）

1. **YAML 解析**：`state/timeline.yaml` 600 章时 803KB，`yaml.parse` 单次 **183ms**（实测），每读一次快照就要解析一次。→ `FsStore.readDoc` 加按 `(size, mtime)` 校验的文档缓存，命中时返回 `structuredClone`（同一文档 3.7ms，实测）。缓存上限 4,096 条（600 章的 1,200 份 review/check + 10 个台账），写入/删除时按路径失效。
2. **journal 重复解析**：一次 `getStatus` 解析 8MB/24,001 行 4–6 次。→ `readJournal` 按 `(size, mtime)` 缓存，返回数组副本。
3. **O(n²) 扫描**：`effortProjection` 对每个章节 × 4 个操作过滤整个 24,001 行 journal = 5,760 万次行访问，这是 `getStatus` 剩余 385ms 的全部；`insight.ts` 的 `archivedAt` 每章 `[...committed].reverse()` 复制 24,001 行。→ 两处都改成一次遍历建 `Map<op, Map<chapter, count>>` / `Map<chapter, archivedAt>`。
4. **attempts 重算**：`reviewAttemptsByChapter` 在 status/report/panel 各算一遍，600 章要读并校验 1,200 份历史 review。→ `attemptsFor` 按 `(root, revision, journal size+mtime)` 记忆，8 条上限。
5. **历史正文**：`queryState {kind:'history'}` 为 `chars` 读每一份历史正文（整章稿）。→ `chars` 改成 `with_chars` 显式开关（新增可选参数，缺省不读），报告/审计都不用它。

### 关键设计取舍（写下来，因为与计划字面不同）

1. **`summary.na === 0` 不能作为 PG-12 的条件**。`na` 同时表示「本章没有对白/没有正文，不适用」和「没人回答」。用 `na === 0` 会让没有对白的章节永远无法归档。改成：`SelfCheckItem.blocking` 只标「缺答」，PG-12 判 `items.some(blocking)`，`summary.unanswered` 计数。区分由 `tests/0219-selfcheck-doc.spec.ts` 的「separates does-not-apply from nobody-answered」钉住。

### 在真实 58 章书上的发现（这才是本轮最有价值的部分）

用 `NOVEL_REAL_PROJECT=<真实书根目录>` 跑 `check-real-project.mjs`，暴露出三个**只有真实书才会出现**的问题：

1. **P1 任务书一条伏笔都装不下**：`open_foreshadows` 97 行、`shown: 0`。原因不是预算不够，而是**单行太大**——一条伏笔带 `advance_log`，即使裁到 120 字仍超过剩余预算，填充循环在第一行就 `break`，整块显示 0 行。修法：窗口行做**深度裁剪**（嵌套数组保留前 3 条、所有字符串裁到 120 字）。裁完 1 行 180 码点，能放进去了。
2. **`book_plan` 1,583 码点，其中 395 是重复的章卡**（`outline_card` 已在上下文里），463 是卷的 goal/arc/climax 全文。修法：删掉重复卡、把卷文本裁到 120/120/120，`book_plan` 降到约 978。省下的空间让 P1 从「1 摘要 + 0 伏笔」变成「1 摘要 + 1 伏笔 + 4 世界观」。
3. **验收脚本本身有两条恒真断言**：`required_omitted` 字段已不存在（`undefined ?? 0 === 0` 永远通过），「至少 8 条伏笔 / 至少 2 条摘要」是 0.2.17 的契约。改成 v2 契约：`context_meta.version === 2`、`fetch` 可解析、每个 `omitted` 块的 `shown > 0`。
