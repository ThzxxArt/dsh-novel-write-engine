# 0.3.0 迭代方案：网文工坊 · 多智能体创作室

> 状态：已实施（实施记录见 `docs/0.3.0-implementation.md`）
> 目标版本：`0.3.0`
> 基线版本：`0.2.15`（2026-11-03）
> 目标宿主：DeepSeek Harness `0.2.2-rc.1` / Cordis `~4.1.0` / Node `>=24.9.0`
> 兼容策略：**不考虑向下兼容，允许破坏性变更**
> 架构策略：**确定性内核 + 确定性编排 + 成熟框架；所有关键选择已拍板**
> 参考：`deepseek-ai/dsh-superagent-prototype`、ABook、Novel OS、InkOS / Novelix、AI_NovelGenerator、ZenStory、MuMuAINovel

---

## 0. 结论先行

0.3.0 不是给 0.2.x 再加几个工具，而是把项目从“单 Agent 写作流水线内核”升级为“**确定性创作内核 + 多智能体创作室**”。

一句话定位：

> **内核负责真相、门控、事务和调度；专属子代理负责规划、写作、评审、连续性与润色；人只做关键决策。**

十二个关键判断：

1. **保留 0.2.x 最值钱的部分**：正文唯一真实来源、单一写入口、门控先于写盘、原子归档、证据链、稳定摘要、可恢复事务。这些不推翻，只重新分层。
2. **拆掉 `EngineService` 上帝类**：14,025 行单文件、11,397 行类、`amendProblems` 693 行、`panelSnapshot` 405 行，已经不适合再叠多智能体。
3. **引入 SQLite 作为编排数据库**：不是把正文塞进数据库，而是把 run/task/lease/event/artifact 索引/评审/成本放进去；正文与设定仍是可读、可 diff、可 git 的文件。
4. **编排必须是确定性的**：不让 LLM 当路由器。Director 是代码，负责 DAG、并发、重试、租约、人工门；LLM 只做创作判断。
5. **每个角色都是 DSH 专属子代理**：用 Agent Preset 定义人格、模型、工具与预算；用 `ctx.subagents.startActivation()` 以 `agentPreset` + `outputSchema` 启动；角色之间不共享自由写权限。
6. **写手不能写台账，审稿人不能改正文，档案员不能改事实之外的正文**：最小权限按角色落到工具注册层，不靠 prompt 约束。
7. **把 28 个模型工具收缩为 10 个模型可见公共工具 + 2 个 host-only 工具 + 角色内私有工具**：主会话不再背 28 个工具的 schema；角色只看到自己需要的 2–4 个工具；工作台人工编辑/审批走 host action，不增加模型工具。
8. **把“上下文预算”升级为“可解释检索”**：SQLite FTS5 + 实体图 + 时间/伏笔/活跃角色加权，每个上下文条目带来源、哈希和入选理由；0.3.0 固定使用 FTS5，不引入向量库。
9. **把“网文工坊”升级为完整工作台**：不是只读报表，而是总览、书稿编辑器、Outline Board、Bible/Codex、Studio Run Board、Review Center、Memory、Analytics、Publish、Settings 十大工作区；人可以直接编辑、批注、对比、批准，所有写入仍经 kernel 版本化。
10. **把 12 个平铺题材升级为 12 大类 / 100 小类 / 137 标签**：大类决定书架，小类决定写法，标签决定卖点与约束；受众、平台独立；标签冲突与依赖可校验。
11. **引入成熟框架，不手搓基础设施**：Drizzle ORM + better-sqlite3、XState、Graphology、Hono、Zod、TanStack、Radix、CodeMirror、React Flow、Recharts、Playwright、fast-check；框架边界写死，不允许运行期替换。
12. **0.3.0 发布门槛**：10 章全链路可跑、任一点 kill -9 可恢复、角色越权为零、取消后零写盘、100 章项目 status < 200ms、现有 1202 项测试的等价覆盖不回退。

### 2.2 结构性债务

#### A. `EngineService` 上帝类

证据：

- `service.ts:704–12101`，约 11,397 行类体。
- `restoreBackup` 约 520 行，4 个分支（2186–2705）。
- `doctor` 约 607 行（4028–4634）。
- `queryStateUnsafe` 约 583 行（3177–3759）。
- `amendProblems` 约 693 行（12956–13648）。
- `panelSnapshot` 约 405 行（9385–9789）。
- `loadAt` 约 401 行（11206–11606）。
- `mutate` 约 402 行（11647–12048）。

后果：任何多智能体改动都会落进同一个类；单测只能靠完整文件系统 fixture；并发/租约/角色权限没有自然落点。

#### B. 存储层已经到极限

证据：

- `journal.jsonl` 每次写都全量 `readJournal`，`assertJournalConsistent` 内多次重复读（`store/journal.ts:68–146`、`351–406`）。
- `reconcileJournal` 扫描所有 committed 记录（`journal.ts:171–212`）。
- `effortProjection` 是 O(chapters × journalRows)（`service.ts:2893–2894`）。
- `doctor` 逐章读正文/review/check（`service.ts:4236–4262`）。
- `FileLock` 在无硬链接回退路径存在 reclaim 竞态（`store/lock.ts:228–235`、`269–283`）。
- 元数据 registry/bindings 非事务、无备份（`store/registry.ts:140–142`、`store/bindings.ts:168–170`）。

后果：多智能体会放大并发和事件量，继续用 JSONL 全量扫描会先撞性能墙。

#### C. 工具面过宽

证据：

- 28 个 `novel_*` 工具集中在 `src/tools/index.ts`（1,486 行）。
- 每个角色都需要完整 schema；模型 token 成本高。
- 读工具和写工具没有角色隔离，靠 prompt 与运行时校验兜底。
- `chapterCardSchema` 暴露了 `status/archived_at/word_count/score` 等引擎字段（`tools/index.ts:303–318`）。
- `arraySemantics`、schema description、服务端行为三份手工维护，存在漂移（`tools/semantics.ts`）。

#### D. 面板单文件

证据：

- `panel.ts` 5,869 行，CSS 1,771 行，624 处 `createElement`。
- 17 个位置参数的 `panelElement`。
- 四代 CSS 叠加；`.nwe-root` 出现 16 次。
- section ETag 清空/304 交互缺陷；共享 `detailController` 导致详情卡死；`aria-controls` 悬空。
- 无 SSE、无虚拟化、无类型化 section。

#### E. 文档与实现漂移

已知至少 21 处（见阅读笔记 I-01..I-21），包括：

- 28 工具 vs 旧注释 18；
- 34 服务操作 vs “32”；
- PG-13 未进入部分迁移表；
- `ready_to_archive --submitRevision--> P4` 未写入设计书迁移表；
- 规则包版本 1.1.0 vs 文档 1.0.1；
- 面板 v6/v7 双版本号；
- `LIMITS.minQuoteChars=12` vs 实际 8 字引文下限。

0.3.0 必须把文档当作发布物的一部分，而不是事后补。

### 2.5 必须保留的 12 条硬约束

从现有 30 条约束中提炼，0.3.0 不因为重构而放弃：

1. 正文是唯一真实来源，`state/` 只是影子。
2. 所有写操作只有一个入口，适配器不直接写文件。
3. 门控先于写盘，失败零变更。
4. 归档必须是一次原子提交。
5. 证据必须可定位到正文；评分必须算术闭合。
6. 轮次由引擎计数，模型不能自报。
7. 规则码唯一 owner，规则包编译后只读。
8. 每个落盘文档有 `schema_version`，过新拒绝。
9. 路径围栏、原子写、写操作串行化。
10. 面板只读，写操作只经 kernel action。
11. 运行时不读外部技能/规则文件，资产随包发布。
12. 覆盖率、证伪测试、架构测试是发布硬门。

## 3. 对标研究

### 3.1 `dsh-superagent-prototype`

它不是小说应用，但它是目前最好的“DSH 原生多智能体长跑”参考。可迁移的 12 个模式：

| 模式                        | 它怎么做                                         | 小说创作室的映射              |
| --------------------------- | ------------------------------------------------ | ----------------------------- |
| Router / Worker 双预设      | 主 Session 只路由，Worker 独立 Session + 目录    | Showrunner / 角色子代理       |
| Ticket                      | 一个授权工作单元，带 Mandate、Assignment、Report | ChapterRun / Task             |
| Mandate                     | 记录授权来源与规则，恢复时重新校验               | 人工批准 + Run 授权           |
| Eval                        | 先规则门，再模型判断                             | 选题/大纲/章节立项            |
| Subscription                | 后续消息进入已有 Ticket                          | 读者反馈/改稿请求进入已有 Run |
| Assignment                  | 每次执行尝试，独立 Session                       | Agent Assignment              |
| Report                      | waiting/ready/blocked/failed/dropped             | Task 结果 + 人工待办          |
| Effects                     | 事务内入队、提交后执行、退避重试                 | 角色调用/事件/写盘后动作      |
| Outbox                      | 消息先存后发、按会话排序                         | 通知/审批/导出                |
| Session + worktree 隔离     | 每 Ticket 独立目录                               | 每章独立工作副本/分支         |
| Prompt 版本 + 团队 override | 版本化、可回滚、记录使用版本                     | 角色 playbook 版本            |
| 管理面板                    | 只显示需要人的事项                               | Run Board + Human Gate        |

明确不照搬的部分：

- 不照搬它的 GitHub/Feishu Source 模型；我们的输入是作者意图、稿件、设定、市场资料。
- 不照搬 `danger-full-access`；小说角色不需要 shell，默认无文件写权限。
- 不照搬它的 SQLite 表结构；我们按 run/task/artifact 重新设计。
- 不照搬“主 Session 只路由”；我们的主 Session 可以阅读、批准、给创作意见，但不直接写正文。

### 3.3 十个可验证的行业结论

1. **分层规划是共识**：书 → 卷/幕 → 弧 → 场景 → 章。单层大纲必漂。
2. **状态必须结构化**：角色位置、资源、关系、伏笔、时间线要能被机器读，不能只靠摘要。
3. **确定性检查要先跑**：连续性/字数/格式/引用先用代码，LLM 只判语义，省 token 且可复现。
4. **审稿与写作必须分离**：审稿人只读，写手不能给自己打分。
5. **改稿要用 patch，不要整章重写**：可审计、可回滚、成本低。
6. **上下文要检索，不要全塞**：分层摘要 + 实体检索 + 预算。
7. **版本/快照是刚需**：作者改一版、AI 改一版，必须能 diff/undo。
8. **多模型路由有价值**：写手用强创意模型，审稿用便宜模型，雷达用本地模型。
9. **人工门不能省**：全自动适合量产，不适合连载质量；0.3.0 固定四道人工门。
10. **产品化差距在 UI**：Run Board、Diff、成本、失败恢复，比多一个 Agent 更重要。

## 4. 0.3.0 目标与非目标

### 4.1 目标

1. **多智能体创作室**：12 个专属角色全部注册；11 个参与章节流水线，Radar 只参与独立 `market` run。
2. **确定性编排**：代码 Director 管任务、租约、重试、人工门、预算；LLM 不做路由。

### 6.2 每个角色的契约

所有角色统一遵守：

```ts
interface RoleContract<T> {
  role: RoleId
  preset: string
  input: {
    task: string
    artifacts: ArtifactRef[]
    canon: CanonSlice
    context: ContextItem[] // 带来源/哈希/理由
    constraints: string[]
    budget: { tokens: number; wallMs: number }
  }
  output: {
    schema: z.ZodType<T>
    structured: T
    citations: Citation[] // 每条关键判断必须引用正文/设定
    confidence: number
    openQuestions: string[]
  }
  permissions: {
    canRead: ArtifactKind[]
    canWrite: ArtifactKind[]
    canCommitCanon: boolean
    canUseNetwork: boolean
    canSpawn: boolean
  }
}
```

硬规则：

1. 角色输出必须通过 Zod 校验；失败一次修复重试，再失败任务失败。
2. 任何“改正文”的 artifact 必须带 `expected_hash` 与 `base_version`。
3. 任何 canon 变更必须带逐字证据锚点（≥8 CJK 或 ≥12 字符）。
4. 角色不能直接写文件；只能调用 kernel 提供的 submit 工具。
5. 角色不能给自己批准；approve 只能由 host 人工通道签发一次性 token 后完成，Showrunner 只能提交 decision 建议。
6. 角色 `canSpawn` 固定为 false；只有 Showrunner 可派生临时 researcher，且 `maxDepth: 1`。

### 6.3 Run / Task / Assignment 三层

```text
Run（一次创作活动）
  ├─ BookRun：bible → outline → volume → chapter batch → publish
  ├─ ChapterRun：plan → draft → review(×3) → revise → continuity → polish → approve → archive
  ├─ RewriteRun：从某个 artifact 版本分支，重跑指定阶段
  ├─ ReviewRun：只对已有章节跑三审 + 连续性，不写正文
  └─ MarketRun：只跑 Radar，产出 MarketBrief，不写 canon

Task（DAG 节点）
  ├─ role + kind + dependsOn + status + attempt + lease
  ├─ input artifact refs
  └─ output artifact ref

Assignment（一次角色执行）
  ├─ agent session id / preset / model
  ├─ provider / structured output / usage
  └─ stop reason / diagnostics
```

状态机：

```text
Run:        queued → running → awaiting_human → paused → completed
                         ↘ failed / cancelled
Task:       pending → ready → leased → running → validating
                         ↘ awaiting_human → completed
                         ↘ retry_wait → running
                         ↘ failed / cancelled / skipped
Assignment: created → started → completed / failed / aborted / max_tokens / refusal
```

### 6.4 标准 ChapterRun DAG

```text
plan
  └─ draft
       ├─ review.story
       ├─ review.character
       ├─ review.prose
       └─ continuity.precheck
            └─ review.merge
                 ├─ (pass) → continuity.final → polish → approve → archive
                 └─ (fail) → revise → draft.revalidate → review.*（最多 3 轮）
```

并行策略：

- 三个 critic + continuity precheck 并行（4 个子代理）。
- 写手唯一，避免同章并发写。
- polish 与 archive 串行。
- 跨章可预取下一章 plan，但不预写正文。
- 全局 `maxActiveSubagents` 默认 6；每项目 `maxWriters=1`。

### 6.5 Agent 调用契约

Director 通过 `ctx.subagents.startActivation()` 启动角色：

```ts
const activation = await ctx.subagents.startActivation({
  provider: 'spawn',
  label: `chapter-${chapter}-${role}`,
  request: {
    parent: directorAgent,
    agentPreset: role.preset,
    cwd: project.root,
    prompt: [{ type: 'text', text: taskPrompt }],
    outputSchema: role.jsonSchema,
    maxDepth: 0,
    agentOptions: role.model ? { model: role.model } : undefined,
  },
  signal: taskSignal,
  delivery: 'caller',
})

const result = await activation.result
try {
  if (result.stopReason !== 'completed') throw new RoleFailure(result)
  const output = role.schema.parse(result.structured ?? parseText(result.output))
  await kernel.artifacts.submit(task, output, {
    agentSessionId: activation.childId,
    preset: role.preset,
    model: role.model,
    usage: result.usage,
  })
} finally {
  await activation.dispose()
}
```

要求：

- 启动前检查 provider capability：`agentPreset`、`outputSchema`、`depthLimit`。
- `outputSchema` 必须落在 DSH 的 `ObjectJsonSchema` 子集内；Zod 生成后要剥离 `$schema`/不支持的 keyword，再通过 `assertObjectJsonSchema`。
- `delivery: 'caller'`，避免子代理结果再注入父会话，减少噪声。
- `maxDepth: 0` 给角色；只有 Showrunner 的临时 researcher 允许 1。
- 每个 assignment 有独立 `AbortSignal`；取消时先 `activation.dispose()`，再标记 task cancelled。
- 结构化输出缺失时，允许从最后 assistant 文本解析一次；仍失败则失败任务。
- 不允许角色复用父会话上下文；spawn（非 fork）保证干净上下文。

### 6.6 会话生命周期与恢复

| 场景         | 策略                                                                             |
| ------------ | -------------------------------------------------------------------------------- |
| 单次任务     | 每次新 spawn，任务结束 dispose                                                   |
| 需要连续对话 | 保存 `childId`，后续用 `ctx.subagents.sendMessage(parent, childId, ...)`         |
| 进程重启     | 未完成 task 的 lease 过期 → 重新 spawn；已完成 artifact 不重跑                   |
| 角色崩溃     | transient 重试 3 次（15s/30s/60s）；内容失败转 revise                            |
| 人工暂停     | run status=paused；不再启动新 task；运行中 task 允许完成或取消                   |
| 取消         | 取消所有 task signal → dispose 子代理 → 等待 quiescence → 标记 cancelled；零写盘 |

### 6.7 人工门

| 门           | 触发                              | 允许动作                                    |
| ------------ | --------------------------------- | ------------------------------------------- |
| Bible Gate   | bible 完成                        | approve / edit / regenerate                 |
| Outline Gate | 全书大纲完成                      | approve / edit / regenerate volume          |
| Chapter Gate | review + continuity + polish 完成 | approve / reject(feedback) / edit / rewrite |
| Publish Gate | 全书完成                          | export / approve cover / hold               |

0.3.0 固定四个门全部强制，不存在跳过门的运行模式。`ReviewRun`/`MarketRun` 不写正文，因此没有人工门，但也不能提交 canon。人工动作写入 `Decision` artifact，带人、时间、理由、目标版本、一次性 `approval_token`。

### 6.8 失败处理矩阵

| 失败               | 处理                                                      |
| ------------------ | --------------------------------------------------------- |
| 模型网络/限流/5xx  | transient retry，指数退避 3 次                            |
| JSON/schema 不合法 | 一次 repair prompt，附规范化错误；再失败 task failed      |
| 字数不足/超出      | 交回 Drafter 的 normalize task，不重跑审稿                |
| 硬门失败           | 生成 revise task，附 gate findings；最多 3 轮             |
| 审稿分歧           | review.merge 任务按权重聚合；blocker 必须一致或人工裁决   |
| 连续性冲突         | continuity finding 进 revise；canon 级冲突交人工          |
| 预算超限           | run paused，保留现场；必须由 host 人工批准新预算后 resume |
| 人工拒绝           | 反馈进 revise，不消耗新一轮 review 计数以外的预算         |

### 6.9 为什么不用 LLM 路由 / 不用 workflow 引擎做核心

| 方案                 | 为什么不用                                                                                |
| -------------------- | ----------------------------------------------------------------------------------------- |
| LLM Router           | 不可复现、成本高、难测试；路由错误会静默跑错流程                                          |
| DSH `workflowEngine` | 执行模型写的 JS 脚本；没有 durable task、lease、human gate、artifact 版本，不适合生产创作 |
| DSH Agent Teams      | 实验性；只有共享任务板/消息，没有 run/artifact/lease/权限模型                             |
| 纯 prompt 编排       | 无法保证顺序、重试、权限、审计                                                            |

结论：**0.3.0 核心只用代码 DAG + DSH Agent Preset/Subagent**。不接入 `workflowEngine`，不接入 Agent Teams，不提供第二条编排路径。所有执行必须经过同一个 Director、同一张 task 表、同一套 lease 与 human gate。

补充：不使用 `ctx.jobs` 作为持久任务队列。`ctx.jobs` 是进程内后台任务，适合把已启动的 run 暴露到宿主 UI；持久状态仍在 SQLite。进程重启后由 scheduler 从 DB 恢复，而不是依赖 jobs 记录。

### 7.2 Artifact 模型

所有角色产物统一为 Artifact：

```ts
interface Artifact<T> {
  id: string
  projectId: string
  kind: ArtifactKind
  chapter: number | null
  version: number
  status: 'draft' | 'reviewed' | 'approved' | 'superseded' | 'rejected'
  path: string
  contentHash: string
  schemaVersion: number
  baseArtifactId: string | null
  provenance: {
    runId: string
    taskId: string
    role: RoleId
    preset: string
    agentSessionId: string
    model: string
    promptHash: string
    createdAt: string
  }
  content: T
}
```

ArtifactKind：

`BiblePlan`、`WorldbookPatch`、`OutlinePlan`、`VolumePlan`、`ChapterPlan`、`Draft`、`ReviewReport`、`ContinuityReport`、`PolishPatch`、`StateDelta`、`Decision`、`MarketBrief`、`Export`。

规则：

- Artifact 版本不可变；编辑 = 新版本。
- `superseded` 保留，用于 diff/回滚。
- 内容哈希覆盖规范化 JSON + 正文；正文文件哈希单独存。
- 归档时只接受 `approved` 的 Draft + 对应 Review + Continuity + Decision。
- 任何 artifact 提交都写 event；event 是审计真相。

| PG-05 | SUMMARY_SCHEMA    | draft/revise       | 十字段摘要                |
| PG-06 | SCENE_TYPE        | plan/draft         | 场景类型与节奏            |
| PG-07 | SCORE             | review/approve     | 15 维算术闭合             |
| PG-08 | ISSUES_CLEARED    | revise/approve     | blocker 必须 fixed + 证据 |
| PG-09 | READING_PROOF     | review/approve     | 三段引文                  |
| PG-10 | CONSISTENCY       | continuity/approve | 跨章规则                  |

| PG-13 | OUTLINE_ALIGNMENT | plan/draft         | 章卡对齐                  |

编辑门控：

| 编号  | 名称                | 判定                                                                   | 级别                                          |
| ----- | ------------------- | ---------------------------------------------------------------------- | --------------------------------------------- |
| EG-01 | VOICE_FINGERPRINT   | 句长分布/对话比/词频 vs `style/fingerprint.json`                       | advisory                                      |
| EG-02 | SCENE_CONTRACT      | goal/conflict/turn/outcome 在正文有落点                                | blocker                                       |
| EG-03 | HOOK_STRENGTH       | 开头钩子 + 结尾悬念（critic + 特征）                                   | advisory                                      |
| EG-04 | PACING_CURVE        | 章内张力曲线 vs 卷弧计划                                               | advisory                                      |
| EG-05 | POV_CONSISTENCY     | POV 视角越界，带证据                                                   | blocker                                       |
| EG-06 | CANON_CONTRADICTION | canon facts / 时间线冲突，带证据                                       | blocker                                       |
| EG-07 | AI_TONE             | `ai_tone` 词库 + 密度 + 跨章重复 + 元叙述；见 `docs/0.3.0-rulepack.md` | P3/P4 advisory；P6/归档 blocker（按阈值升级） |

原则：

- 确定性检查先跑，LLM 只补语义。
- 每条 finding 必须带 `location` + `evidence`；无法定位的 finding 降为 advisory 或拒绝。
- 门控结果写 `gate_result`，approve 只读最近一次通过的 gate set。
- 门控不得依赖 prompt 文本；规则码唯一 owner。

### 7.5 评审与评分 v2

保留 150 分制，但拆成三份独立评审 + 一份合并：

| 评审       | 维度                                 |                        权重 |
| ---------- | ------------------------------------ | --------------------------: |
| Story      | 结构、节奏、因果、爽点、钩子、商业性 |                          60 |
| Character  | 动机、声音、关系、成长、POV          |                          45 |
| Prose      | 句式、描写、对话、去 AI 味、格式     |                          30 |
| Continuity | canon/时间线/伏笔/资源               | 15（独立 gate，不计入 150） |

合并规则：

- 三个 critic 各自输出 `dimension deductions`，kernel 合并为 15 维总分。
- 同一 finding 由多个 critic 命中时按 `location+rule` 去重，保留最重。
- blocker 必须至少一个 critic 给 blocker，或 continuity 给 blocker。
- 分数不等于质量；分数只做门槛，人工看 finding。

### 7.6 Canon / State Delta v2

`state/canon.yaml` 是正文的影子，不是第二真相。结构：

```yaml
schema_version: 2
entities:
  characters: [...]
  locations: [...]
  factions: [...]
  items: [...]
  concepts: [...]
relationships: [...]
timeline: [...]
foreshadows: [...]
resources: [...]
```

`StateDelta`：

```ts
interface StateDelta {
  chapter: number
  entities: Array<{
    key: string
    kind: 'character' | 'location' | 'faction' | 'item' | 'concept'
    action: 'created' | 'updated' | 'no_change'
    reason: string
    evidence: string       // 正文逐字锚点

  relationships: [...]
  timeline: [...]
  foreshadows: [...]
  resources: [...]

```

规则：

- `no_change` 必须带 `reason`。
- `created` 必须能在正文找到名字/锚点。
- `updated` 必须给出 before/after + 证据。
- 资源 `set` 与 `add` 双通道，同章双写拒绝。
- 伏笔 `resolved` 必须有 `resolved_anchor`。

- 任何 canon 变更由 Archivist 提交，kernel 校验，不能由 Drafter 直接写。

### 7.9 规则包 v2 与 AI 味词库

0.3.0 的规则包从“词表 + 阈值”升级为“词表 + 上下文 + 密度 + 跨章重复 + 可解释替换”。完整设计见 **`docs/0.3.0-rulepack.md`**。

固定结论：

1. `schema_version: 2`，`version: 2.0.0`；0.2.x 规则包不兼容，必须重写。
2. 新增 `lexicon.ai_tone` 段，包含 7 个类别、39 条 entry、覆盖 50+ 个高频 AI 味短语/模板。
3. 新规则码：`AI_TONE_META`、`AI_TONE_ACK`、`AI_TONE_COMPARATIVE`、`AI_TONE_PROTECTIVE`、`AI_TONE_SOCRATIC`、`AI_TONE_TEMPLATE`、`AI_TONE_JUDGMENT`、`AI_TONE_DENSITY`、`AI_TONE_REPEAT`。
4. 检测顺序：归一化 → 引号/对白分段 → exact/regex/template 匹配 → 跨度去重 → 上下文分级 → 窗口密度 → 跨章重复 → 升级 severity。
5. P3/P4 只给 advisory 与替换建议；P6/归档由 `EG-07` 升级为 blocker。元叙述出现在旁白中直接 blocker；对白中先 advisory。
6. 密度阈值：1000 非空白字符内同一类别超过 `limit` 升级一级；不同类别 ≥3 或总命中 ≥5 触发 `AI_TONE_DENSITY` blocker。
7. 跨章重复：同一 entry 连续 2 章出现，或 10 章内出现 ≥3 次，触发 `AI_TONE_REPEAT` blocker。
8. 误报豁免：动作语境（“下盘很稳”“手很稳”）、具体对象比较（“这块铁比那块重”）、正常动作“把账记下了”不命中；每个角色允许 1 个 signature phrase，但仍计入密度。
9. 规则包编译期新增 10 条断言：id 唯一、term 归一化去重、regex 可编译且长度受限、template 只允许 `{xx}`/`{xxx}`/`{ta}`、category 存在、severity 合法、limit/window 合法、scope 合法、`standalone` 只用于 judgment、默认包必须覆盖 canonical phrase list。
10. `R-W-07（去 AI 味，4 分）` 是唯一评分映射；reviewer 的 deduction 必须引用 `AI_TONE_*` 规则码，kernel 校验 finding 与 deduction 一致。

### 7.10 类型体系 v2：大类 / 小类 / 标签

0.3.0 把 0.2.x 的 12 个平铺题材升级为三级类型体系。完整清单见 **`docs/0.3.0-genres.md`**。

固定结论：

1. **12 个大类**：幻想、都市、历史、科幻、悬疑、游戏竞技、言情、现实、轻小说、同人、互动叙事、短篇实验。
2. **100 个小类**：每个大类 6–11 个，ID 固定为 `<major>.<sub>`。
3. **137 个标签**：分 11 个 facet：世界观 18、主角 14、情节 26、风格 12、主题 12、设定 14、结构 8、视角 5、情感 8、节奏 8、市场 12。
4. **五轴分离**：大类、小类、标签、受众、平台各自独立；受众 `male/female/general/teen/adult`，平台 `fanqie/qidian/qimao/jinjiang` 不塞进标签。
5. **项目必填**：1 个大类 + 1 个属于它的小类 + 3–12 个标签 + 1 个受众 + 1 个平台。
6. **标签约束**：每 facet 最多 3 个；冲突标签双向拒绝；`requires` 缺失拒绝并给建议；至少 1 个 `tone` 或 `theme` 标签。
7. **稳定排序**：`world,prot,plot,tone,theme,set,struct,pov,emo,pace,market` + tag ID；brief/digest 不因输入顺序变化。
8. **规则优先级**：`tag > sub > major > global`；只允许白名单键覆盖（伏笔休眠、对话比、段长、水词、pleasure_keywords、lexicon_add/remove）；同一组标签对同一键冲突时保存/编译拒绝。
9. **旧 12 类型**：只做单向映射到“小类 + 推荐标签”；导入报告要求作者确认，不静默改写。
10. **工作台**：创建项目用级联选择器；标签按 facet 分组、搜索、冲突灰显、依赖提示、规则预览；Settings 修改类型生成新版本。
11. **测试**：G-01..G-12 覆盖数量/ID/父级/冲突/依赖/facet 上限/digest/旧映射/profile 冲突/级联/导入/优先级/未知引用。
12. 0.3.0 不接受自由文本类型；新增类型走 taxonomy 版本，不走运行时配置。

## 8. 存储与事务

### 8.1 为什么是 SQLite

| 需求       | YAML + JSONL          | SQLite                                      |
| ---------- | --------------------- | ------------------------------------------- |
| 多任务并发 | 文件锁 + 全量 journal | WAL + 行级事务                              |
| 任务查询   | 全量扫描              | 索引                                        |
| 租约/重试  | 自建                  | 事务 + 条件更新                             |
| 事件流     | 追加文件              | event 表 + seq                              |
| 全文检索   | 无                    | FTS5                                        |
| 成本统计   | 无                    | 聚合查询                                    |
| 崩溃恢复   | pending 推断          | WAL + checkpoint                            |
| 迁移       | 手写                  | Drizzle Kit migration + schema_migration 表 |

结论：**SQLite 只做编排/索引/审计，不做正文真相**。正文、设定、大纲仍是文件，可 git、可 diff、可人工编辑。

### 8.2 数据库位置

`<project>/.studio/studio.db`，WAL 模式，`busy_timeout=5000`，`foreign_keys=ON`。

全局注册表/会话绑定统一迁到 `~/.dsh/novel-write-engine/studio.db`。0.3.0 不再保留 YAML 元数据实现，避免两套事务与备份语义。

### 8.4 事务边界

| 操作                                 | 事务                                                               |
| ------------------------------------ | ------------------------------------------------------------------ |
| 创建 run + 首批 task                 | 单事务                                                             |
| 领取 task（lease）                   | `UPDATE ... WHERE status='ready' AND lease_until IS NULL` 条件更新 |
| 提交 artifact + 完成 task + 写 event | 单事务                                                             |
| 批准 + 创建下一批 task               | 单事务                                                             |
| 归档 + canon 更新 + manuscript 状态  | 单事务 + 文件 staging                                              |
| 取消                                 | 事务标记 + signal 传播                                             |

文件与 DB 不能同一个事务，所以采用：

1. Artifact 内容先写 staging 文件，算 hash。
2. DB 事务插入 artifact 引用 + task 完成 + event。
3. DB 提交后 rename staging → 正式路径。
4. 若 rename 失败，写 compensating event，task 标 failed，artifact 标 orphan。
5. 启动时扫描 orphan/未 rename 的 staging，修复。

### 8.5 租约与恢复

- task 领取：`lease_owner = directorId`，`lease_until = now + 5min`。
- 心跳：运行中每 30s 刷新 lease。
- 崩溃：lease 过期，scheduler 用条件更新抢占，`attempt += 1`。
- `attempt > max_attempts` → `failed`，写 event，run 进入 `awaiting_human`。
- 已完成 artifact 的 task 不重跑；按 `run_id + role + chapter + base_artifact_id` 幂等。
- 取消：`run.status=cancelled`，所有 task `cancelled`；运行中的 assignment 先 dispose，再标记。

### 8.6 备份、快照、回滚

- SQLite 每日/每次 run 前 `VACUUM INTO` 或 `backup()` 到 `.studio/backups/`。
- Artifact 内容寻址，天然可回滚；DB 只存引用。
- `novel_artifact restore <id>` 创建新版本，不删除历史。
- 全书快照：DB backup + `bible/outline/manuscript/state` 的 manifest（路径+hash）。
- `novel_rewind <run|artifact|chapter>`：恢复到指定版本，生成新 run，不覆盖历史。

### 8.7 旧项目导入

0.3.0 不双读 0.2.x。提供单向导入：

```bash
dsh novel import ./old-project --to ./new-project
```

导入器：

1. 读 `novel.yaml` + `state/*` + `outline/*` + `chapters/*` + `reviews/*` + `checks/*`。
2. 转成 `studio.yaml` + `bible/` + `outline/` + `manuscript/` + `state/canon.yaml`。
3. 旧 review/check 转成 `reviews/ch-xxxx/legacy.yaml`，标记 `imported_legacy`。
4. 旧 journal/backups 复制到 `.studio/legacy/`，只读保留。
5. 导入后跑 `doctor` + `export` 校验；不自动继续写。

#### 9.6.3 稿件编辑器

- **CodeMirror 6** 纯文本编辑器，不引入富文本；正文禁止 Markdown，格式门控实时提示。
- 中文写作体验：全角标点、段落缩进、焦点模式、打字机模式、行宽限制、深浅色。
- 实时统计：总字数、汉字数、对话比、段长、句长；与 kernel 口径一致。
- 评审高亮：finding 的 `location/evidence` 在正文中高亮；点击 finding 跳转段落。
- 评论：选区评论、@角色、解决/重开；评论进入下一轮任务上下文，但不构成授权。
- 版本：自动保存本地草稿；`保存版本` 生成新 Draft artifact；版本列表、双栏 diff、恢复为新版本。
- 人工编辑：`human_edit` host-only action，带 `base_hash`；保存前跑格式门控；不消耗 review 轮次；下一轮 review 以新 hash 为准。
- 拆分视图：左侧正文、右侧评审/版本/上下文；可拖拽宽度。
- 导出单章：Markdown/TXT/EPUB 片段。

#### 9.6.4 大纲工作台

- 三层视图：书 → 卷/幕 → 弧 → 章卡；支持拖拽排序、跨卷移动、合并/拆分章。
- 章卡字段：标题、场景类型、POV、cast、目标/冲突/转折/结果、目标字数、钩子、伏笔、notes。
- 张力曲线：按章卡 beat 生成，叠加目标曲线；偏离过高/过低给 advisory。
- 伏笔板：planted/advanced/resolved 三列；显示年龄、计划回收章、逾期；拖拽推进。
- 角色弧矩阵：角色 × 卷/章，显示出场、成长节点、关系变化。
- 生成动作：`生成卷`、`生成章卡`、`补齐空卡`、`dry-run 预览`；全部生成 artifact，经人工门落盘。
- 与稿件联动：点击章卡跳到对应正文；正文改动可回写章卡状态（经 kernel）。

#### 9.6.5 设定 / Codex

- 实体类型：角色、地点、势力、物品、概念、规则、术语、历史事件。
- 每个实体：概要、canon facts、首次出场、最近出场、关系、锚点、版本、反链。
- 关系图：React Flow + dagre 自动布局；按关系类型过滤；点击边查看证据。
- 时间线：横向/纵向两种布局；事件与章节关联；时间回归高亮。
- 反链：每个实体显示出现在哪些章、哪些 review、哪些伏笔。
- 编辑：字段级表单 + 版本；锁定字段需要显式解锁；canon 变更走 `WorldbookPatch` + 人工门。
- 导入/导出：YAML/Markdown；旧项目导入的设定只读标记。

#### 9.6.6 创作室 / Studio

- **Run Board**：列：Queued / Leased / Running / Awaiting Human / Retry / Done / Failed；Review、Revise 作为任务类型泳道聚合，不作为状态列。卡片显示角色、模型、attempt、tokens、耗时、artifact。
- **DAG**：React Flow + dagre；节点按状态着色；点击节点看 assignment、输入 context、输出 artifact、错误。
- **Agent Roster**：12 个角色、preset、模型、状态、最近任务、累计 tokens/成本；支持 spawn 临时 researcher、interrupt、查看会话。
- **实时流**：选中 assignment 的 agent 消息/工具调用/token 流；SSE 推送；可暂停滚动。
- **控制**：启动 BookRun/ChapterRun/RewriteRun/ReviewRun/MarketRun；暂停/恢复/取消；重试失败 task；提高预算需人工 token。
- **人工门 Inbox**：Bible/Outline/Chapter/Publish 四类；显示 diff、证据、gate 结果；approve/reject/edit。
- **Trace**：run → task → assignment → event 四层；可导出 JSONL。

#### 9.6.7 评审中心

- 三列并排：Story / Character / Prose；第四列 Continuity。
- 每条 finding：维度、severity、location、evidence、problem、fix、status；点击 evidence 在正文高亮。
- 合并视图：按 `location+rule` 去重，显示最重；blocker 必须一致或人工裁决。
- 评分：15 维条、总分、与上一轮对比、与卷均值对比。
- 动作：accept/waive（仅 advisory）、转 revise、批量选择、生成修订任务。
- 轮次：历史轮次并排 diff；显示每轮谁改了什么、分数变化、blocker 关闭情况。

#### 9.6.8 记忆 / 检索

- 全局搜索：FTS5，支持 scope（稿件/摘要/大纲/设定/canon/review）、章节、角色、伏笔、时间。
- Context Inspector：任选 task，查看实际送入的 context 条目、score、reason、protected、token 占比。
- 检索测试：输入 query，查看 top-k、分数拆解、来源。
- 索引健康：chunk 数、stale 数、last rebuild、失败条目；重建索引。
- 导出：context 包 JSON，用于调试/复现。

#### 9.6.9 分析

- 进度：卷/章完成度、字数、预计剩余。
- 质量：评分趋势、维度雷达、blocker/advisory 比例、返工次数。
- 节奏：张力曲线、钩子强度、场景类型分布、对话比、段长分布。
- 角色：出场次数、最近出场、POV 分布、关系热度。
- 伏笔：年龄、回收率、逾期、motif 比例。
- 成本：run/chapter/role/model 的 tokens 与费用；预算使用率。
- 导出：CSV/JSON/PNG。

#### 9.6.10 发布

- ExportProfile：平台、卷/章标题规则、作者的话、简介、标签、封面。
- EPUB 预览：目录、封面、章节、字体/行距；导出前校验。
- 发布包：EPUB + 平台元数据 + 章节清单 + gate 校验报告。
- 发布检查：所有章节 approved/archived、canon 一致、无 blocker、封面/简介/标签齐全。
- 历史导出：版本、时间、目标平台、校验结果。

#### 9.6.11 设置 / 健康

- 模型路由：每个角色的 provider/model/reasoningEffort；连接测试。
- 预算：per chapter/run/task；超限策略固定为暂停并请求人工。
- 角色：preset 列表、权限、playbook 版本。
- 项目：目标、平台、质量阈值、review 轮数。
- 备份：DB backup、artifact 版本、恢复点。
- Doctor：DB integrity、lease、orphan artifact、canon 引用、preset、gate、索引。
- 迁移：旧项目导入、schema migration、回滚。

#### 9.6.12 交互与状态

- **命令面板**：Cmd/Ctrl+K；所有工作区动作、跳转、搜索、运行控制。
- **快捷键**：Cmd/Ctrl+S 保存版本、Cmd/Ctrl+Enter 运行、Cmd/Ctrl+Shift+Enter 批准、J/K 上下章、G 然后 S 进创作室、? 帮助。
- **多选/批量**：章节、finding、任务；批量批准/导出/重试。
- **拖拽**：大纲卡、章卡、关系图节点；落下后调 kernel，不做本地最终写。
- **通知**：Sonner toast + 通知中心；人工门/失败/预算/完成。
- **状态分层**：
  - TanStack Query：服务端资源、ETag/SSE 失效、分页。
  - Zustand：布局、选中、tab、编辑器缓冲、命令面板。
  - XState：Run 控制、审批流、导入流、发布流。
  - 本地草稿：IndexedDB/localStorage 只存未提交文本；提交必须回 kernel。
- **一致性**：所有写操作先显示 pending，收到 kernel event 后更新；失败回滚 UI 并显示错误。
- **离线**：只读缓存可用；写操作禁用；恢复后重放未提交草稿需用户确认。

#### 9.6.13 协议

- `GET /api/novel-write-engine/v8/bootstrap?root=...`：项目、角色、能力、版本。
- `GET /api/novel-write-engine/v8/board?root=...`：run/task/agent 快照。
- `GET /api/novel-write-engine/v8/events?root=...`：SSE，事件带 `seq`；`Last-Event-ID` 重连。
- `GET /api/novel-write-engine/v8/artifact?root=...&kind=...`：分页/差分。
- `GET /api/novel-write-engine/v8/search?root=...&q=...`：FTS。
- `POST /api/novel-write-engine/v8/action`：host-only 动作（编辑、审批、运行控制、导入/导出），带 CSRF/审批 token。
- 所有 GET 只读；POST 只接受 host 通道，模型工具不能直接调用。
- Hono 路由 + SSE helper；统一错误 JSON `{code,message,hint,details}`。
- DTO 从 `contracts/dto.ts` 的 Zod schema 推导，客户端不手写镜像类型。
- `ctx.locale.register('novel-studio', { zh, en })`；所有文案走字典。

#### 9.6.15 可访问性与响应式

- WCAG 2.2 AA；Radix 原语保证键盘/焦点/ARIA。
- Tabs：roving tabindex + 方向键；非激活 panel 用 `hidden` 保留 `aria-controls`。
- 所有图标按钮有 `aria-label`；所有图表有文本摘要；所有 finding 可用键盘操作。
- 深浅色主题；跟随宿主 token；对比度自动检查。
- 响应式：≥1280 三栏；768–1279 两栏 + Inspector 抽屉；<768 单栏 + 底部导航。
- `prefers-reduced-motion` 关闭动画；触屏目标 ≥44px。

#### 9.6.16 设计语言

- **Token**：只使用宿主 `--dsw-alias-*` 与插件 `--nwe-*` 两层 token；禁止硬编码颜色。
- **排版**：UI 用无衬线；正文默认衬线，项目设置可显式改为无衬线；16–18px，行高 1.8，最大行宽 38em。
- **密度**：默认舒适密度；8px 网格，12/16/24 间距；表格/看板紧凑但不小于 32px 行高。
- **状态色**：queued 灰、running 蓝、awaiting 琥珀、failed 红、done 绿；颜色之外必须有图标/文字。
- **动效**：150ms ease-out；只用于状态变化和抽屉；`prefers-reduced-motion` 全部关闭。
- **空态/错误态/骨架**：每个工作区都有；错误必须带 code、message、hint、重试。
- **阅读优先**：无装饰性渐变、无大面积动画；正文区域避免浮层遮挡。

### 9.7 MCP / HTTP API

- 保留只读 HTTP 工作台 API，统一到 v8。
- 固定提供 MCP server：`novel_status`、`novel_run`、`novel_approve`、`novel_artifact`、`novel_search`、`novel_export`。
- MCP 读接口固定只读；写操作必须带 `project_root` + 一次性 `human_approved` token，且只能调用 host-only action。
- MCP 与面板共用同一 kernel action 表，不新增第二条写路径。

0.3.0 不保留分叉。以下 14 条是实施约束，不是建议；实现时不得引入第二套方案。

|   # | 决策        | 固定结论                                                                                                                    | 理由                                           |
| --: | ----------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
|   1 | 包名/产品名 | 包名保留 `dsh-novel-write-engine`；产品名“网文工坊 · 创作室”                                                                | 保留安装标识与发布历史                         |

|  10 | DSH         | 只支持 `0.2.2-rc.1` 及以上 0.2.x；不兼容 0.2.1                                                                              | 使用 Agent Preset、Subagent、conditional tools |

### 19.1 确定性实现规则

1. 任何一个业务动作只能有一个实现入口；不存在 “A 路径 / B 路径”。
2. 任何一个状态只能有一个 writer；其他模块只读或发命令。
3. 任何一个 artifact 只能有一个 schema；Zod 是唯一源。
4. 任何一个 run 只能经过同一张 task 表、同一套 lease、同一套 gate。
5. 任何一个框架只能在一个边界目录出现；升级走独立 ADR。
6. 任何一个“可选功能”都不进入 0.3.0；要么固定实现，要么明确不做。
7. 任何一个失败都必须留下 event、diagnostic、可恢复点；不允许静默吞错。
8. 任何一个 UI 写操作都必须回 kernel；不允许面板直接改文件或直接改 DB。

```sql
  created_at TEXT NOT NULL,

  ended_at TEXT
);

  id TEXT PRIMARY KEY,
  run_id TEXT NOT NULL REFERENCES run(id) ON DELETE CASCADE,
  role TEXT NOT NULL,
  kind TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('pending','ready','leased','running','validating','awaiting_human','retry_wait','completed','failed','cancelled','skipped')),
  depends_on_json TEXT NOT NULL DEFAULT '[]',

  error TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_task_run_status ON task(run_id, status);
CREATE INDEX IF NOT EXISTS idx_task_output_artifact ON task(output_artifact_id);
CREATE INDEX IF NOT EXISTS idx_task_lease ON task(status, lease_until);

CREATE TABLE IF NOT EXISTS assignment (
  id TEXT PRIMARY KEY,
  task_id TEXT NOT NULL REFERENCES task(id) ON DELETE CASCADE,
  agent_session_id TEXT,
  provider TEXT NOT NULL,
  preset TEXT NOT NULL,
  model TEXT,
  status TEXT NOT NULL CHECK (status IN ('created','started','completed','failed','aborted','max_tokens','refusal')),
  stop_reason TEXT,
  usage_json TEXT,
  started_at TEXT,
  ended_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_assignment_task ON assignment(task_id);

CREATE TABLE IF NOT EXISTS artifact (
  id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  kind TEXT NOT NULL,
  chapter INTEGER,
  version INTEGER NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('draft','reviewed','approved','superseded','rejected')),
  path TEXT NOT NULL,
  content_hash TEXT NOT NULL,
  schema_version INTEGER NOT NULL,
  base_artifact_id TEXT REFERENCES artifact(id),
  provenance_json TEXT NOT NULL,
  created_at TEXT NOT NULL,
  UNIQUE(project_id, kind, chapter, version)
);
CREATE INDEX IF NOT EXISTS idx_artifact_lookup ON artifact(project_id, kind, chapter, status);

CREATE TABLE IF NOT EXISTS event (
  seq INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id TEXT NOT NULL,
  run_id TEXT,
  task_id TEXT,
  type TEXT NOT NULL,
  payload_json TEXT NOT NULL,
  at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_event_project_seq ON event(project_id, seq);

CREATE TABLE IF NOT EXISTS gate_result (
  id TEXT PRIMARY KEY,
  artifact_id TEXT NOT NULL REFERENCES artifact(id) ON DELETE CASCADE,
  gate TEXT NOT NULL,
  verdict TEXT NOT NULL CHECK (verdict IN ('pass','fail','advisory')),
  details_json TEXT NOT NULL,
  at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_gate_artifact ON gate_result(artifact_id, gate);

CREATE TABLE IF NOT EXISTS review_finding (
  id TEXT PRIMARY KEY,
  artifact_id TEXT NOT NULL REFERENCES artifact(id) ON DELETE CASCADE,
  role TEXT NOT NULL,
  dimension TEXT NOT NULL,
  severity TEXT NOT NULL CHECK (severity IN ('blocker','advisory')),
  location TEXT NOT NULL,
  evidence TEXT NOT NULL,
  problem TEXT NOT NULL,
  fix TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('open','fixed','waived'))
);

CREATE TABLE IF NOT EXISTS memory_chunk (
  id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL,
  kind TEXT NOT NULL,
  chapter INTEGER,
  source_path TEXT NOT NULL,
  source_hash TEXT NOT NULL,
  text TEXT NOT NULL,
  meta_json TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_memory_project_kind ON memory_chunk(project_id, kind);

CREATE VIRTUAL TABLE IF NOT EXISTS memory_fts USING fts5(
  text,
  content='memory_chunk',
  content_rowid='rowid'
);

-- FTS5 外部内容表需要同步触发器（insert/update/delete），
-- 否则 memory_chunk 更新后检索会陈旧。迁移脚本必须一并创建。
CREATE TRIGGER IF NOT EXISTS memory_chunk_ai AFTER INSERT ON memory_chunk BEGIN
  INSERT INTO memory_fts(rowid, text) VALUES (new.rowid, new.text);
END;
CREATE TRIGGER IF NOT EXISTS memory_chunk_ad AFTER DELETE ON memory_chunk BEGIN
  INSERT INTO memory_fts(memory_fts, rowid, text) VALUES ('delete', old.rowid, old.text);
END;
CREATE TRIGGER IF NOT EXISTS memory_chunk_au AFTER UPDATE ON memory_chunk BEGIN
  INSERT INTO memory_fts(memory_fts, rowid, text) VALUES ('delete', old.rowid, old.text);
  INSERT INTO memory_fts(rowid, text) VALUES (new.rowid, new.text);
END;

CREATE TABLE IF NOT EXISTS model_usage (
  id TEXT PRIMARY KEY,
  run_id TEXT NOT NULL,
  task_id TEXT NOT NULL,
  role TEXT NOT NULL,
  model TEXT NOT NULL,
  prompt_tokens INTEGER NOT NULL,
  completion_tokens INTEGER NOT NULL,
  cost_usd REAL NOT NULL DEFAULT 0,
  at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_usage_run ON model_usage(run_id, role);
```

## 附录 C：Run 状态机

```text
                 ┌──────────────┐
                 │    queued    │
                 └──────┬───────┘
                        │ start
                        ▼
                 ┌──────────────┐
      ┌─────────│   running    │─────────┐
      │         └──────┬───────┘         │
      │ human gate     │ all tasks done   │ error
      ▼                ▼                  ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│awaiting_human│  │  completed   │  │   failed     │
└──────┬───────┘  └──────────────┘  └──────┬───────┘
       │ approve                            │ retry
       └──────────────► running ◄───────────┘
       │ reject
       ▼
   (revise task)

任何 running 状态可 → paused → running
任何 running/paused 可 → cancelled
```

Task 状态机：

```text
pending → ready → leased → running → validating → completed
                    │         │          │
                    │         │          └→ awaiting_human → completed
                    │         └→ retry_wait → running
                    └→ failed / cancelled
```
