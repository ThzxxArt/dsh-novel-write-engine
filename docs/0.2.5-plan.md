# 0.2.5 迭代方案：让 P6 与归档的错误归因、轮次和恢复都说真话

> 状态：待实施
> 基线：v0.2.4 / `9a23ed9`（已发布，848 项测试、CI 10/10）
> 审计日期：2026-10-30
> 审计范围：`src/` 60 个文件、`tests/` 83 个文件、`docs/` 19 篇、`briefs/` 8 篇、`skills/` 1 篇；另只读检查真实项目 `/mnt/d/BookWorkspace/1971从偷渡港岛开始`
> 本方案不改代码，只定义 0.2.5 的范围、契约、任务和验收。

## 1. 结论

三个实测问题**全部在当前 v0.2.4 上复现**，不是旧版本残留：

| 编号 | 严重度 | 实测结论 | 当前代码根因 |
| --- | --- | --- | --- |
| I1 | **P1** | 5 条语义项中 4 条引文逐字存在、跨句；引擎把 4 条都报成“overlap/same sentence”，真正的缺失项排在最后 | `semantic.ts` 要求引文完整落在一个句子内；跨句引文永远不满足 |
| I2 | **P2** | 已在 worldbook 的实体出现在 `summary.new_elements` 时，`created`、`updated`、省略三种写法全部被拒 | `state-delta.ts` 同时要求“新元素必须 created”和“created 不能已存在” |
| I3 | **P2** | 5 条形式的语义错误（少一条、引文不存在）会消耗 3 次 check 轮次，第 4 次正确提交被 PG-11 拒绝 | `runCheck` 把所有 semantic finding 都算作内容失败；非数组还静默变成 `[]` |

真实项目已经留下证据：

- `history/checks/ch003.r0075.check.yaml`：4 条双句引文 + 1 条不存在的 POV 引文，`verdict: fail`。
- `history/checks/ch003.r0076.check.yaml`：5 条逐字引文全部 `verdict: pass`，但 `verdict: fail`，`machine.violations` 为空。
- `history/checks/ch003.r0082.check.yaml`、`r0085`：同一份正文只把引文截成单句，`verdict: pass`。
- `state/journal.jsonl`：`04:39:51` 的 `runCheck` 被 `PG-11 ... check 3` 拒绝；`04:40:48` / `04:40:58` 的两次 `archiveChapter` 分别报“九记茶楼已存在”和“九记茶楼是新的，必须 created”。
- 归档后 `state/chapters.yaml` 第 3 章仍记录 `review:5 / revise:3 / check:5 / rollbacks:1`；这不是模型写作质量问题，而是引擎把证据形状错误算成了内容失败。

**0.2.5 的主目标不是增加写作功能，而是把 P6 校验与归档的错误归因、轮次预算和可恢复性修到“调用方知道下一步该改什么”。**

## 2. 三个实测问题的根因与修法

### 2.1 I1：跨句/跨段证据被误判为 overlap

**根因**

`src/engine/semantic.ts:26-37` 的 `sentenceSpans` 只在 `。！？!?` 处切句，且没有处理：

- 段落换行；
- 行尾的 `」』”"）】` 等收尾符号；
- 引文跨两个句子或两个段落。

随后 `:128-149` 要求整段引文必须落在一个 `sentenceSpans` 内：

```ts
const sentenceIndex = sentences.findIndex(
  (candidate) => start >= candidate.start && end <= candidate.end,
)
```

跨句引文的 `sentenceIndex === -1`，即使 `overlaps === false`，也会落入 `:142-148` 的通用错误：

```text
cites overlapping text or the same sentence as another check
```

而 `briefs/P6.md:25` 只要求“五条互不相同、来自不同句子的引用”，没有要求“每条必须在一句内”。这是**实现比文档更严格**，并且错误信息把三种完全不同的原因合并成“overlap”。

真实 r0076 中 4 条引文都跨句：

```text
（已脱敏，同形合成）
旧楼停电。守门人正在收伞。
三枚铜钱。他口袋里一枚也没有。
最后两趟，伙计忘了盖章。账本写着九十二，碟子洗出一百零三。
没有通行证就是没有通行证。你在铺头站一个钟，也是犯法。
```

只有 POV 的“他把脸转开，看见路边的牌子。”是单句，所以它通过，其余 4 条全部被报 overlap。

**修复契约**

1. `sentenceSpans` 以“段落边界 + 句末标点 + 行尾收尾引号”为边界。
2. 引文允许跨句/跨段；按**字符区间**判断：
   - 引文必须在正文中逐字存在；
   - 引文区间不得与已接受证据区间重叠；
   - 引文覆盖的每个句子都不得已被其他证据使用；
   - 接受后把覆盖的所有句子标为已使用，并记录区间。
3. 错误必须按条目区分：
   - `NOT_FOUND`：正文完全找不到；
   - `TOO_SHORT`：少于 8 字；
   - `DUPLICATE`：与另一条引文完全相同；
   - `OVERLAP`：与已接受区间重叠，detail 指出冲突的 item id；
   - `SAME_SENTENCE`：没有区间重叠，但复用了已用句子，detail 指出冲突 item id；
   - `BOUNDARY`：只用于真正无法归入句子的异常（修复后不应再出现）。
4. `novel_check` 返回 `semantic.items`（每条 `id/status/quote/nearest?`）和 `semantic.findings`；失败时 `CheckDocument.semantic` 也保存 findings，避免出现“5 条 pass、verdict fail、无解释”的 check 文件。
5. `nearest` 只用于 `NOT_FOUND`：返回最接近的段落号、截断到 120 字的段落文本和相似度，不替代逐字校验。

**验收**

- 5 条真实双句引文 → 5 条 OK，`verdict: pass`。
- 4 条真实双句引文 + 1 条编造引文 → 只有编造项 `NOT_FOUND`，其余 4 条 OK，且不出现 OVERLAP/SAME_SENTENCE。
- 两条引文来自同一句的不同子串 → 仍拒绝 `SAME_SENTENCE`。
- `走吧。」她点点头` 这类行尾收尾引号 → 接受。
- 单条跨句引文（没有其他 item）→ 必须通过，不能报“another check”。

### 2.2 I2：world delta 对“新元素/已存在实体”的两个真源互相否决

**根因**

`src/engine/state-delta.ts` 同时存在两条规则：

- `:363-383`：`summary.new_elements` 中的每个名字必须 `action: created`；
- `:412-424`：`created` 时如果 `findWorld(name) !== null`，报“already exists; use updated or no_change”。

于是：

```text
summary.new_elements 有“九记茶楼”
+ state/world.yaml 已有“九记茶楼”
→ created 被 :424 拒绝
→ updated 被 :379/:414 拒绝
→ 省略被 :375 拒绝
```

`summary.new_elements` 是 P3/P8 的叙事意图，不是 world ledger 的写操作；当前实现却把两者当成同一个 owner。真实项目 `journal.jsonl` 的 `04:40:48` 和 `04:40:58` 两行就是完整证据；`state/world.yaml` 中九记茶楼是第 2 章建立的。

> 术语澄清：这里说的 worldbook 是 `state/world.yaml` 归档台账，不是 `outline/worldbook.yaml` 设定集。`findWorld` 只读 `state/world.yaml`；0.2.5 的 PG-05 也应只把该台账视为“已存在”的真源。

另一个问题：归档失败后 `archivePreflight` 不检查 delta，`nextStep` 仍返回 `novel_archive` 和“all gates pass”；模型会反复尝试同一个不可能成功的调用。

**修复契约（选择 B：ledger 存在性为唯一真源）**

只对 `world` 实体做 reconcile，不改 characters/foreshadows/timeline/relationships 的严格语义：

1. `findWorld(name) !== null`：
   - `created` → 归一化为 `updated`，写 change 记录，返回 warning `WORLD_ELEMENT_RECLASSIFIED_CREATED_TO_UPDATED`；
   - `updated` / `no_change` → 正常；
   - `kind` 与现有 kind 冲突 → 仍拒绝；
   - `detail` 改写 reserved 字段 → 仍拒绝。
2. `findWorld(name) === null`：
   - `updated` → 在能确定 kind（显式 `kind` 或 `summary.new_elements` 类别）且正文出现该名字时归一化为 `created`，返回 warning `WORLD_ELEMENT_RECLASSIFIED_UPDATED_TO_CREATED`；
   - 无法确定 kind 或正文未提及 → 拒绝，但 hint 必须给出“declare kind / add to new_elements”的可执行路径；
   - `no_change` + summary 新元素 → 归一化为 `created`（正文必须提及），warning；
   - `created` → 正常。
3. `summary.new_elements` 只做校验，不再强制 action：
   - 名称必须在正文出现；
   - 类别与实体 kind 一致；
   - 已存在实体不再要求 created，返回 `WORLD_ELEMENT_ALREADY_IN_LEDGER` warning。
4. `DeltaResult` 增加 `warnings` 与 `normalized_world`；`archiveChapter` 把它们放进 `OpResult.warnings`；`novel_archive` 通过现有 `withWarnings` 展示。
5. `archivePreflight` 对“delta 形状可预检”的错误返回 `novel_archive` 修复提示，不再谎报 all gates pass；真正的 delta 校验仍在 archive 事务内执行。
6. 文档更新：`DESIGN.md:1767` 当前明确写“created 已存在、updated 不存在一律拒绝”，必须改为“world 以 ledger 存在性为准，冲突归一化并 warning”；P8 brief 同步。

**验收**

- 已存在实体 + summary.new_elements + `created` → 单次 archive 成功，按 updated 落账，warning 可见；
- 已存在实体 + summary.new_elements + `updated` → 成功；
- 新实体 + `updated` + 可推断 kind + 正文出现 → 成功，按 created 落账；
- 新实体 + `updated` + 无法推断 kind → 单次失败，hint 可直接修；不需要 P5；
- 真实 `九记茶楼` 场景 → 不需要 `novel_revise`、不需要改 summary，直接 archive；
- 原有 `created` 新实体、`updated` 已存在、`no_change` 带 reason 的测试仍通过。

**明确不采用**

- 不把 `characters/foreshadows/timeline/relationships` 全部改成 upsert；它们的 `created/updated` 是显式义务清单，当前问题只来自 `summary.new_elements` 与 world ledger 的双真源。
- 不靠“改 summary”作为唯一出路；summary 是 P3 证据，不该为了绕过归档而被重写。

### 2.3 I3：校验形状错误消耗 content 轮次

**根因**

`src/engine/service.ts`：

- `:4611`：`const semantic = Array.isArray(input.semantic) ? input.semantic : []`；非数组被**静默**变成空数组；
- `:4647-4649`：`evaluateSemantic` 的任意 blocking 都让 `verdict = 'fail'`；
- `:4683-4694`：所有 semantic blocking 都进入 `pipeline.blocking`；
- `:4698-4701`：`rounds.check + (verdict === 'fail' || fullScope ? 1 : 0)`；
- `gates.ts:544-561`：PG-11 在下一次提交前直接阻断。

所以 `SEMANTIC_MISSING`、`SEMANTIC_ITEM_INVALID`、`SEMANTIC_EVIDENCE_INVALID` 和真正的 `SEMANTIC_CHECK_FAILED` 共用同一个轮次预算。真实项目三个 check 都是证据形状/缺失问题，check 从 0 到 3，第 4 次正确检查被 PG-11 拒绝，只能 rollback。

另外，`nextStep` 对 P6 的任意 blocking 返回 `novel_revise`，于是引文笔误会把模型送去改正文。

**修复契约**

把一次 check 分成三类结果：

| 类别 | 例子 | 是否写 check 文档 | 是否消耗 `rounds.check` | 后续 next |
| --- | --- | --- | --- | --- |
| `submission` | 非数组 semantic、缺项、多 ID、item 字段错误、引文过短/不存在/重复/同句/重叠 | 否 | 否 | `novel_check`（重新提交正确证据） |
| `content` | 五项合法且逐字存在，但某项 `verdict:"fail"`；machine blocker | 是 | 是 | `novel_revise` |
| `pass` | 五项合法且全部 pass，无 machine blocker | 是 | 否 | `ready_to_archive` 或 partial scope 留在 P6 |

具体：

1. 在 `runCheck` 写文档前调用 `validateSemanticSubmission(text, semantic)`，返回 `SemanticItemResult[]` 和 `failure_class`。
2. `semantic` 不是数组、item 不是对象、ID 缺失/重复/未知、缺五项、引文为空/短/不存在/重叠/同句 → 抛 `CheckSubmissionError`（新增 `ENGINE_CHECK_SUBMISSION_INVALID`）：
   - 不写 `checks/chNNN.check.yaml`；
   - 不改 `pipeline.blocking`/`rounds`；
   - journal 仍由 `mutate` 写 aborted attempt（保留审计）；
   - 错误消息和 `items` 明确列出每条状态，其他合法项显示 OK。
3. 只有 `content` 类失败才写 check、设置 blocking、把 `rounds.check +1`；`pass`（含完整 scope）不增加轮次。
4. `CheckDocument` 增加可选 `semantic.findings`（`BlockingItem[]`）、`failure_class`、`counted`；旧 check 文档无这些字段仍可读，不升 `schema_version`。
5. `novel_check` 的 `data` 增加 `semantic`（items/findings）与 `rounds`；工具和命令都能看到，不再只返回 `violations: 0`。
6. `nextStep`：
   - content fail → `novel_revise`；
   - submission fail → 不把旧 blocking 当成内容 blocker；下一次仍是 `novel_check`（至少不能在错误提示里推荐 P5 改正文）。
7. 真实项目回归：两个形状错误 + 一个 content fail → `rounds.check === 1`，随后正确 check 可以继续；三个 content fail 才触发 PG-11。

**兼容性**

- 旧 check 文档的 `verdict/rounds` 含义不变；只改变 0.2.5 之后新提交的分类。
- `SEMANTIC_EVIDENCE_INVALID` 作为旧 persisted code 保留可读；新结果使用具体 reason/status，避免破坏旧历史。
- 非数组 semantic 从“静默 [] + fail”改为明确 schema 错误；这是修正，不是兼容回归。

## 3. 完整审计发现的额外问题

以下不是用户最初三条，但在全量读取中确认，按“是否进入 0.2.5”标注。

### 3.1 0.2.5 必须修（release blocker）

#### B1 P1：pending 事务在只读面上被误报为外部篡改

证据：

- `src/store/txn.ts:245-256` 在第一次 rename 前写 pending row；
- `src/store/journal.ts:167-208` 的 `reconcileJournal` 只看 committed；
- `:218-261` 的 `recoverPending` 只在写路径的 `assertJournalConsistent` 调用；
- `src/engine/service.ts:2261-2317`（`journalBlocking`）、`:3104-3143`（doctor）、`:5482-5533`（audit）只调用 `reconcileJournal`；
- `readJournal`（`journal.ts:116-136`）不把 pending 放进用户可见 rows。

后果：崩溃发生在“所有 rename 已完成、committed row 未写”的窗口时，status/doctor 报 `JOURNAL_HASH_MISMATCH`，hint 让用户“restore from backups”；照做会把已经逻辑提交的事务回滚掉。若 pending 只有部分 rename，doctor 反而可能 `ok=true`，项目不可写却显示健康。

修法：新增只读 `inspectPending(store)`，分类 `none | complete | untouched | partial`；status/doctor/audit/panel 使用它；complete → `PENDING_RECOVERABLE`（warning，不误报 hash mismatch），untouched → `PENDING_ABORTABLE`（warning），partial → `PENDING_PARTIAL`（error，指向 staging/before）；写路径仍由 `recoverPending` 实际 promotion/abort。另：`novel_init` 在 `PROJECT_EXISTS` 检查前对 pending 做恢复/拒绝，修复“崩溃 init 永远无法重新初始化”的路径（`service.ts:8469-8555`）。

#### B2 P1：outline 卷/归档卡不变量只在 `novel_outline` 生效

已实测/代码确认：

- `novel_outline {volumes:[...]}` 改写 omitted 的归档卡 `volume`，返回 `updated:[]`；`normalizeOutlineChapters` 还会给 `archived_at:null` 的归档卡补 `now`，伪造归档时间。见 `outline-merge.ts:288-324`、`book.ts:724-735`。
- `novel_blueprint` 直接 remap 所有卡（`service.ts:1206-1223`），没有 `assertArchivedVolumes`；已实测归档章 1 在卷 1-3，改成 2-3 后卡 `volume:null`，卷不再覆盖归档章。
- `novel_outline_import` 只调用 `assertActiveCardPreserved`，不复用归档卷守卫；`novel_amend` 的 outline 修复只校验结构。
- `assertActiveCardPreserved` 在 `strict:false` 时直接返回（`service.ts:6549-6564`），但 `novel_outline` 的 active remove 无条件拒绝；两条入口不一致。

修法：

1. 抽 `assertArchivedCardVolumes(snapshot, existingCards, nextVolumes, operation)`，由 `submitBookPlan`、import preview+apply、amend 的 outline 校验共用；归档章失去卷覆盖 → `ENGINE_SCHEMA_INVALID`，hint 指向 `novel_reopen` 或保留原卷。
2. `mergeOutline` 的最终 cards 与 `existingByNum` 做稳定 JSON diff，把归档回填/reindex 放进 `updated` 或新 `reindexed` 列表；`dry_run` 返回 `would_update/would_reindex`，不能静默。
3. 不伪造 `archived_at`；omitted 卡保留原值，只有显式提交才允许改。
4. active card 保护与 strict 解耦：import 也不得删除活动章卡（否则至少要求显式 confirm，0.2.5 直接拒绝）。
5. import dry-run 必须跑 apply 相同的 `assertArchivedCardVolumes` + `assertActiveCardPreserved` + `assertOutlineWritable`。

#### B3 P2：没有 summary-only 修复路径，PG-05 又把新元素错误留到 P8

证据：

- `submitRevision` 要求 content/patch 二选一（`service.ts:4309`），没有 summary-only；
- `briefs/P8.md:95` 让模型用 P5 revise 修 summary，结果真实项目用相同正文做“summary-only”修订，仍消耗 revise，并强制 P4 评审 + P6 check；
- PG-05 只检查 `new_elements` 是字符串数组（`gates.ts:206-213`），不检查正文是否提及、也不检查 world ledger 是否已有；
- 真实项目 `04:38:57` 的 `六婶家` 错误直到 archive 才被发现，成本是一轮 P5/P4/P6。

修法：

1. 允许 `novel_revise` 只带 `summary`（content/patch 都省略）的 **summary-only** 模式：正文 hash 不变、不写 chapter/history、只更新 `pipeline.draft.summary`，校验 PG-05；不增加 revise 轮次（或使用独立 `summary` 预算，0.2.5 先不消耗 revise）。
2. PG-05 在 P3/P5 就检查 `summary.new_elements`：
   - 名字必须在正文出现；
   - 名字如果已在 world ledger，报“remove from new_elements or use updated/no_change”；
   - `characters_appeared` 必须在正文出现（允许 narrator alias）。
3. P8 brief 改为“summary-only 修复不需要改正文，也不该重跑 P4”；同时保留 content 修复必须走 P5 的规则。

#### B4 P2：`current_state.resources` 整体替换，且可写入负余额

`state-delta.ts:287-291` 只做一层 merge，`resources` 被整体替换；`:325-334` 只在 `resource_changes` 上做非负校验，`current_state` 没有。P8 brief 自己的示例 `{"resources":{"港币":-3}}` 会写成绝对负值。

修法：深合并 `resources`；对 `created/updated` 后的每个余额校验有限非负整数；非数字余额拒绝；修复 P8 brief 示例。验收：负余额拒绝、保留兄弟资源、字符串余额拒绝。

### 3.2 0.2.5 应修（可排在同一 release 的后半）

- **B5 P2 brief digest 只签裁剪后的 context**：`service.ts:3650-3652` 用 context 算 digest，`fields.book_plan` 是完整 plan；700 字 premise 只改 600 字之后，PG-01 仍通过。修法：digest 加入完整 outline/worldbook/planning 文档 hash（或 `fields` hash），并补 700 字尾部变化测试。

## 5. 契约与数据模型

### 5.1 Check

新增（均为 additive，旧文档可读）：

```ts
type SemanticItemState =
  | 'pass' | 'fail' | 'missing' | 'invalid' | 'not_found'
  | 'too_short' | 'duplicate' | 'overlap' | 'same_sentence'

interface SemanticItemResult {
  id: string
  state: SemanticItemState
  quote?: string
  detail?: string
  nearest?: { paragraph: number; quote: string; score: number }
  conflict_with?: string
}

interface CheckSubmissionError extends EngineInputError {
  readonly items: SemanticItemResult[]
  readonly passed: number
  readonly failed: number
  readonly rounds_consumed: 0
}
```

`CheckDocument`（可选字段）：

```ts
semantic: {
  items: SemanticItem[]           // 保留原样，历史兼容
  findings?: BlockingItem[]       // 新：可解释失败
}
failure_class?: 'submission' | 'content'
counted?: boolean
```

`runCheck` 成功返回新增：

```ts
semantic: { items: SemanticItemResult[]; findings: BlockingItem[] }
rounds: { check: number }
counted: boolean
```

只有 `failure_class='content'` 才写 check 并 `counted:true`；submission 抛错，不写 check。

### 5.2 State delta

`DeltaResult` 新增：

```ts
warnings: Warning[]
normalized_world: Record<string, {
  from: DeltaAction
  to: DeltaAction
  reason: 'existing-created-as-updated' | 'missing-updated-as-created' | 'missing-no-change-as-created'
}>
```

`archiveChapter` 的 `data` 增加 `delta_warnings`（或复用 `OpResult.warnings`），不改变 `assigned_ids/metrics/score`。旧 state_delta 输入格式不变。

### 5.3 Pending

新增只读（不写）类型：

```ts
type PendingState = 'none' | 'complete' | 'untouched' | 'partial'
interface PendingInspection {
  state: PendingState
  txid?: string
  files?: string[]
  detail?: string
  stagingDir?: string
}
```

`status/doctor/audit/panel` 只读消费；写路径的 `recoverPending` 使用同一分类逻辑。

### 5.4 Outline

`mergeOutline` 结果增加 `reindexed: number[]`；`dry_run` 增加 `would_reindex`。归档卡 `volume`/`archived_at` 的 omit 语义与显式提交分开。共享 `assertArchivedCardVolumes` 返回 `BlockingItem`/错误 hint。

### 5.5 错误码

新增：

- `ENGINE_CHECK_SUBMISSION_INVALID`
- `ENGINE_PENDING_PARTIAL`（或复用 `ENGINE_TXN_ABORTED` + code）
- `ENGINE_IO_PERMISSION`（或 `ENGINE_PROJECT_UNREADABLE`）
- `SEMANTIC_EVIDENCE_NOT_FOUND / TOO_SHORT / DUPLICATE / OVERLAP / SAME_SENTENCE`
- `WORLD_ELEMENT_*` warning codes

`SEMANTIC_EVIDENCE_INVALID` 保留用于旧历史读取；新结果优先具体 code。

## 9. 迁移与兼容
