## 历史、备份与 effort

- 首次归档后 `history/` 尚无前版本可保存；`novel_reopen` → 重新 P3/P4/P6/归档后，两个项目都有 3 条历史：
  - `history/reviews/ch001.rNNNN.review.yaml`
  - `history/checks/ch001.rNNNN.check.yaml`
  - `history/chapters/ch001.rNNNN.md`
- 两个项目的 `novel_state {kind:"backups"}` 均为 9 个备份，覆盖 `archiveChapter`、`reopenChapter`、`submitDraft`、`submitReview`、`runCheck`、`submitBookPlan`、`submitWorldbook`；`runCheck`/`submitReview` 的 pre-image 可被 `novel_restore` 实际恢复（单元测试覆盖）。
- `report.effort` 在重开并重新归档后仍保留 lifetime `reviews=2`、`checks=2`、`rollbacks=0`，`ChapterRecord.final_check=pass` 未被重开清零。

## 短稿门禁的真实证据

- 本次 2.5 的第 1 次 P3 为 76 字，被驱动脚本的 300 字下限拒绝；第 2 次模型误输出摘要而非正文，脚本检测到缺少 `content` 后重试；这两次都发生在 `submitDraft` 之前，不算 PG-03 证据。
- 更早一次 2.5 运行在 600 字目标下产出 564 字，真实调用 `submitDraft` 时被 PG-03 拒绝（477 汉字 + 85 标点 + 1 英文词 + 1 数字）；该临时项目的 journal 仍保留 `status:"aborted"` 证据。
- 因此本文只把 564 字算作 PG-03 证据；76 字这类是驱动脚本的临时目标下限，不冒充引擎门控。

## 覆盖范围

两个项目都完成：`novel_init` → 蓝图 → 世界书（含 `facts`）→ P1 → P2 → P3 → P4 → P6 → P8 归档 → report/doctor/panel/history/backups → 六种导出 → `novel_reopen` → 重新 P3/P4/P6/归档 → 最终 `stage=done`。P1/P2/P3 使用真实模型；P4/P6 使用确定性夹具；临时项目保留在 `/tmp` 供复核。

## 结论

两条真实模型链路都能在 0.2.1 上从开书走到归档、全量观测、六种导出、重开与重新归档；P1 的角色被 P2/P3 继承，0.2.1 的新面板 v3、历史记录、备份 manifest 与 lifetime effort 在真实事务中均可见。PG-03 对 564 字短稿的真实拒绝发生在更早一次运行；本次 76 字由驱动脚本下限拦截，未进入引擎。两者都说明没有为了“跑通”而伪造字数证据。
